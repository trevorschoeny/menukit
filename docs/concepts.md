# Concepts

Definitions of the terms MenuKit coins and the rules that bind consumer code. Every other page links here rather than redefining a term.

## MenuKit and SlotKit

MenuKit is one mod, `menukit`. It runs on the client and the server: the UI draws on the client, and the Kits built on MenuKit use its placement types and its declarations freeze on the server too. It holds no slot code. Slot groups, slot operations, created slots, custom menus and per-slot state are SlotKit's (`slotkit`), a separate library that depends on MenuKit. MenuKit does not depend on SlotKit, so a mod that depends on MenuKit alone cannot import a SlotKit type. The build fails. SlotKit's terms are on [SlotKit's concepts page](https://github.com/trevorschoeny/slotkit/blob/main/docs/concepts.md). A mod moving from MenuKit 6 follows [upgrading-7.md](upgrading-7.md).

## Public API

The API is the `api` packages: `com.trevlar.menukit.api.*`. [Versioning](versioning.md) covers them. Every other package carries `@ApiStatus.Internal` and is outside the contract, so a mod that calls into one can break in any release. MenuKit has a common half and a client half, and the compiler keeps screen code out of the common half. The `api` packages span both halves. A class that names a screen type is client-only, and its javadoc says so.

## Panel

A `Panel` is a bounded rectangle that holds an ordered list of elements. It renders, receives input, and shows or hides as one unit. It has an id, a `PanelStyle`, a padding, and a visibility.

Panels do not nest. A panel holds elements. It does not hold other panels.

Panel ids are global. Prefix every id with the mod id: `"mymod:controls"`. Namespaced ids matter more from 7.4.0 on, since what keys on a panel id (a player's stored position for a panel, a panel several mods share) keys across every mod installed.

## Element

A `PanelElement` is one item inside a panel. Its position is relative to the panel's content area. MenuKit ships these elements:

| Kind | Types |
|---|---|
| Render only | `TextLabel`, `Icon`, `Divider`, `ItemDisplay`, `ProgressBar`, `InfoBox` |
| Interactive | `Button`, `Toggle`, `Checkbox`, `Radio` (with `RadioGroup`), `Slider`, `TextField`, `Dropdown`, `DropdownMulti`, `ItemPicker`, `ColorField` |
| Composite | `ScrollContainer`, `Flow`, `Section`, `Tabs`, `ListView`, `ConfirmDialog`, `AlertDialog`, `EditDialog` |
| Host | `WidgetHost`, for a vanilla-style widget made outside MenuKit |
| Slot (SlotKit) | `SlotElement`, `SlotFlowElement`, in SlotKit |

A consumer implements `PanelElement` for a custom element, or extends `AbstractPanelElement`.

An element wholly outside the clip it is drawn in, such as a row scrolled out of a `ScrollContainer` or a container region section out of view, is not rendered. It gets `renderCulled(ctx)` instead of `render(ctx)` each frame, so it can tell being out of view from being hidden: a slot element keeps its slot parked rather than handing it back to the menu's layout. A hidden element (its `visibleWhen` false, or inside a hidden or collapsed parent) gets neither call. The default does nothing. A custom element that holds other elements forwards `renderCulled` to its shown children with `ChildDispatch.renderCulled`, as MenuKit's own containers do, so the call reaches every element under a culled one.

## Builders and one vocabulary

Every element is built by its builder and does not change after `build()`: `Button.builder()...build()`. The same idea has the same name on every builder:

| Method | Meaning |
|---|---|
| `at(x, y)` | Position in the panel's content area. |
| `size(w, h)` | Size, on the elements that take one. The rest size themselves from their content. |
| `visibleWhen(supplier)` | Shown while it holds, read every frame. |
| `disabledWhen(supplier)` | Grayed and inert while it holds. On a container it disables everything inside. |
| `tooltip(text)` | The hover tooltip, fixed or read every frame. A `\n` in the text starts a new line. `tooltip(first, more...)` takes several lines, each in its own style. |
| `state(get, set)` | The lens onto the consumer's value (see State). |
| `onClick(Runnable)` | What a press does. |
| `opaque(boolean)` | Whether the element is solid on a transparent panel. |
| `declId(id)` | A stable id for the element's window address. |

No builder picks a look. An element draws in the look of the screen it is on (see Looks).

An instance keeps only what a container needs. That is `setChildPosition(x, y)`, which a `Flow`, `Row` or `Column` uses to place its children, and the layout calls a panel makes every pass. Anything that varies at runtime is read from a supplier.

## Mouse buttons

An element receives left clicks through its primary callback. `Button` and `Toggle` also accept `onSecondaryClick(Consumer<Click>)`, which receives every non-left button.

A `Click` record carries the button index and the shift, control, and alt state sampled when the click reaches the element. It answers `isRight()`, `isMiddle()`, `isShiftRight()`, and `isSecondary()`. On macOS the command key counts as control.

With no secondary handler attached, non-left clicks pass through to vanilla. A disabled control consumes neither kind.

## Keyboard, sound and narration

`Button`, `Toggle`, `Checkbox` and `Radio` behave as vanilla widgets do. A click plays vanilla's click sound. Tab moves keyboard focus onto them in screen order, and a focused control draws its hover look. Enter or Space presses the focused one. The narrator reads its label and, for the boolean controls, its on or off state. `Slider` and `TextField` are vanilla's own `AbstractSliderButton` and `EditBox`, exposed through `widget()` and hosted by a `WidgetHost` (see Widget host). An element that is not drawn (its panel hidden, its section closed, its tab not shown) cannot take focus.

While a modal panel is shown on a vanilla screen, a key goes to the panels' elements first. Escape then runs the modal's `onEscape`. Any other key then goes to the focused widget if MenuKit placed it (a dialog's text field, for instance). After that the key is dropped, so the screen under the modal never acts on it. Keys vanilla handles outside the screen still work: F11, the F3 combinations, the narrator hotkey and screenshots.

## Tint

`Button` and `Toggle` accept `tint(IntSupplier)`. The supplier runs each frame and returns an ARGB value. The tint fills the control inside its border, over the background and under the label. Returning 0 draws no tint. The tint shows consumer-owned state, such as a pinned mode, that the control itself does not store.

## State

A stateful element is only a lens onto the consumer's value. `state(get, set)` reads the value from `get` every frame and hands a change to `set`. The element stores nothing. A value changed elsewhere shows at once, and a setter that refuses a change shows the refusal on the next frame. Persistence belongs to the consumer. `Toggle`, `Checkbox`, `Slider`, `TextField`, `Dropdown`, `DropdownMulti`, `ItemPicker` and `ColorField` require a `state`. A `Radio` reads its `RadioGroup.state(get, set)`.

Some state is the element's own view state, not the consumer's. Examples are whether a `Section` is open, a `ScrollContainer`'s scroll, a `Tabs` body's scroll, and whether a dropdown's popover is open. `Section` and `ScrollContainer` take a `state(get, set)` to hand theirs to the consumer. `Tabs` takes `bodyScroll(get, set)`, in pixels keyed by tab id. A screen that rebuilds itself (a new `MKScreen`, a new `Tabs`) hands these over, so it reopens as the player left it.

`Slider` and `Dropdown` take typed lenses for whole numbers and enums: `Slider.ofInts(min, max)`, `Slider.ofEnum(Mode.class)`, `Dropdown.ofInts(min, max)`, `Dropdown.ofEnum(Mode.class)`. Their `state` and `label` take `Integer` or the enum. `Slider.builder()` is the 0 to 1 fraction.

## Disabled

`disabledWhen` on an element grays it and makes it inert. `Panel.disabledWhen(supplier)` does the same for every element of the panel, and a container's own `disabledWhen` (a `Section`, `Tabs`, `ScrollContainer` or `Flow`) does it for everything inside. Text grays too. `TextLabel`, `InfoBox` and a section's header draw in the disabled gray, which is the screen kind's `TextRole.DISABLED` color. A disabled panel still claims its area, so what is behind it stays inert. Its elements take no clicks, wheel or keys. Mouse releases still arrive, so a drag can end.

## Looks

There are two looks, the Panel look and the Default look, and every element draws in the look of the screen it is on (since 6.1.0). There is one set of elements, and nothing else picks a look. Before 7.3.0 the two were `ScreenKind.CONTAINER` and `ScreenKind.OPTIONS`; those names still work, deprecated, until 8.0.0.

| Look | Screens | How it draws |
|---|---|---|
| Panel, `ScreenKind.PANEL` | Inventories, chests, anything built on vanilla's `AbstractContainerScreen` | MenuKit's: raised gray controls on a light gray panel, dark text without a shadow. Under a resource pack that restyles containers or vanilla's widgets, the pack's (7.4.0, below) |
| Default, `ScreenKind.DEFAULT` | The screens reached from the pause menu and the title screen: Options, Video Settings, Controls, Create World | Vanilla's: stone buttons, vanilla's checkbox, tab and slot sprites, white text with a shadow, separators and the darker list band, over the blurred world or the panorama |

The look comes from the screen, by one rule (`ScreenKind.of(screen)`):

- A panel injected into a vanilla screen. An `AbstractContainerScreen` has the Panel look, and any other vanilla screen the Default look. A panel on Controls draws in the Default look with no code.
- An anchor's panels are in the look of the screen the anchor is on.
- A standalone `MKScreen` is in the look it declares when it is created, `super(title, ScreenKind.DEFAULT, panels)`. One that declares none has the Panel look, which every standalone screen had before 6.1.0. `screenKind()` reads it back. A library's own screen declares its look to its `OwnHost`.
- The HUD has the Panel look, the look it has always had.
- A dialog or any other panel on a screen is in that screen's look, and so is the dialog an `ItemPicker` opens.

The kind travels with the frame in `RenderContext.kind()`, and `at` and `disabledIf` keep it. An element built from other elements passes it on without reading it. The kind changes how an element draws, never its size or behavior.

Text takes its color from a role: `TextRole.HEADING`, `BODY`, `MUTED` or `DISABLED`. `ScreenKind.textColor(role)` resolves it. In the Panel look the colors are dark gray (`TextLabel.COLOR_DARK`) for headings and body, `ElementConstants.TEXT_MUTED` for muted text and the disabled gray for disabled text, all without a shadow (`textShadow()`). In the Default look they are vanilla's own white, `CommonColors.GRAY` and `CommonColors.LIGHT_GRAY`, with a shadow. A `TextLabel` is `BODY` unless `role(...)` sets another role. The labels of a checkbox, a radio button and a section's header follow the same table. `color(argb)` fixes a color in both looks. Text on a control (a button's label) is white on both.

What each piece draws in the Default look, from vanilla's 26.2 sprites:

| Piece | In the Default look |
|---|---|
| A panel's background | `RAISED` is vanilla's popup frame (`popup/background`, the box of its own warning popups), `INSET` the list band, `DARK` unchanged, `NONE` nothing. A dialog reads as vanilla's own. |
| `Button`, `Dropdown`, `DropdownMulti` | `widget/button`, `button_highlighted` on hover, `button_disabled`; the popover on `button_disabled` |
| `Toggle` | A vanilla button whose text is the state: its label, or vanilla's `ON` / `OFF` without one |
| `Checkbox` | `widget/checkbox`, `checkbox_selected` and their `_highlighted` sprites, at MenuKit's 10 px box |
| `ItemPicker` | `container/slot`, the slot the Superflat layer list draws its blocks in |
| `Section` | The Controls screen's category header colors: the title white, the summary gray, read from the left as on a container screen |
| `Divider` | Vanilla's separator, `Screen.HEADER_SEPARATOR` (2 px) |
| `ScrollContainer` | The list band: `menu_list_background` behind the content, a separator directly outside it above and below, and vanilla's thin list scroller. The content is inset a little more than in vanilla's lists, `DEFAULT_INSET_X` (14) from the left and `DEFAULT_INSET_Y` (10) above and below. It is narrower by that much, as `viewportWidthFor(width, kind)` reports. In a dialog (a modal panel) the inset is the dialog's own gap, `DIALOG_INSET` (4), on every side it insets, because the frame and padding already make the margin |
| `Tabs` (`WRAP`, `SIDE_SCROLL`) | Create World's tab bar: white labels, the selected one underlined and open into a page of the list background, the separator either side of the tabs. The page insets the body as the list band does, from both sides, and lays it out that much narrower |
| `Slider`, `TextField` | Vanilla's own widgets in both looks |
| `ColorField` | Its swatch is a vanilla button with the color inside. Its dialog is a dialog of the screen, so its tabs, buttons and hex field draw for the kind |
| `WidgetHost` | Whatever the hosted widget draws. It draws itself, the same in both looks |

Where vanilla has no counterpart (a radio button, an info box, a progress bar, a consumer's sprite), the element keeps MenuKit's drawing in both looks. While a world is open the separators and the list band use vanilla's in-world textures, as vanilla does.

The Panel look follows the active resource pack (7.4.0). A raised panel's frame, fill and slot frames are cut from the pack's chest art, controls draw vanilla's button and checkbox sprites where a pack restyled them, and text on a panel keeps its role's color wherever that reads on the pack's fill and takes one made from the fill where it doesn't. A pack can also override MenuKit's own sprites to theme it directly. A mod has nothing to do. With no pack the Panel look is exactly as before. [Resource packs](resource-packs.md) has the order a look is chosen in and the sprites a pack can override.

## Item picker

An `ItemPicker` is a setting whose value is an item or a list of items. On the page it is one slot. For a list it is a wrapping row of slots in order, `columns(n)` to a row (9 by default), ending in an empty slot marked with a plus. Each filled slot has a small remove button over its top-right corner, a few pixels showing a minus, with the tooltip "Remove". A click on it, or a right click anywhere on the slot, empties the slot. In a list that drops the slot, and the items after it move up one place. A left click anywhere else on a slot (or Enter on the focused picker) opens a dialog at that slot. On hover a slot shows the item's own tooltip, followed by how the setting compares it.

The value is always whole stacks, read from `get` every frame and handed to `set` on every change:

| Lens | Value |
|---|---|
| `state(Supplier<Item>, Consumer<Item>)` | One item, the kind only. `Items.AIR` is none. The 6.1.0 lens, unchanged. |
| `stack(get, set)` | One `ItemStack`. `ItemStack.EMPTY` is none. |
| `stacks(get, set)` | A `List<ItemStack>` in the player's order, never with empty entries. |
| `rule(get, set)`, `rules(get, set)` | The same as `ItemMatch` values, each a stack and its own match mode. |

`match(ItemMatch.Match)` declares how the setting compares stacks. `ItemMatch` does the comparing, so a mod never writes its own. Call `rule.matches(stack)`, or `ItemMatch.matches(config.stack, ItemMatch.Match.EXACT, stack)` for a plain stack.

- `ITEM`, the default: the kind of item only. Count and components are ignored. The dialog has no Edit tab, and every slot holds one plain item.
- `EXACT`: vanilla's own stack equality, the same item, count and components. A rule with nothing set is a plain item, so an enchanted or renamed one does not match.
- `CONTAINS`: the same item and at least the components the rule sets. The count is ignored. A rule with nothing set matches any variant. Components compare as vanilla's item predicates compare them: enchantments must be there at their level (more may be), custom data must contain the rule's tag, a component the rule removes must be absent, anything else must be equal.

A rule can leave chosen component types out of `EXACT` and `CONTAINS`: `rule.ignoring(DataComponents.DAMAGE)` still matches the item once it is worn, since neither side's damage is looked at. The count is not a component, so `rule.ignoringCount()` leaves it out of `EXACT` (the other modes never compare it). The picker's `ignoring(...)` and `ignoringCount()` declare the same once: every rule it writes carries them, and with `ignoringCount()` the Edit tab has no count. A `stack` or `stacks` lens stores plain stacks, so test those with a rule built the same way, `new ItemMatch(stack, EXACT).ignoring(DataComponents.DAMAGE)`. `ItemMatch.CODEC` saves what a rule ignores, and a rule saved without it loads ignoring nothing.

The mode decides whether an empty rule means "any" or "plain", so MenuKit never guesses. `playerChoosesMatch()` lets the player choose per slot between `Any <item>` (`CONTAINS`) and "Exactly this" (`EXACT`). It needs `rule` or `rules`, which store the choice, and `match` sets the choice for a new slot. `ItemMatch.CODEC` saves a rule with vanilla's stack codec.

The dialog is a modal dialog of the screen, in its kind. It is laid out as every dialog is, and is as wide and as tall as the tab it shows. At the top is the slot row, the setting's slots with the selected one outlined. A click on a slot selects it, and it stays selected until another is clicked. Each filled slot has the same remove button as on the page. It empties the slot, and in a list it also drops the slot, so the slots after it move left. The Search tab comes first. It has a search box, focused so typing starts at once, over a grid of every item from the creative inventory's search tab. Each potion, tipped arrow, enchanted book level, goat horn, firework duration and ominous bottle is its own entry (with `ITEM`, each item appears once). Search reads names, ids and tooltips. A click on an entry puts one of it straight into the selected slot, replacing what was there, and the slot stays selected. The Edit tab's count sets more (with `ITEM` there is no count). Enter in the search box puts the first match in the selected slot the same way. The grid asks for its nine columns, so the dialog is always wide enough to show them whole. In a list, filling the slot at the end adds a new empty one after it, to select and fill next.

The Edit tab, for `EXACT` and `CONTAINS`, edits the selected slot. It has the slot's name and count, then its enchantments in two lists. Under "Added" are those on the item, each with its level, `-` and `+` buttons from I to its highest, and a remove button. Under "Not Added" are those that fit the item and can be added, each with an add button. One that an enchantment on the item excludes is grayed and says what it conflicts with. An item nothing enchants lists none, and an enchanted book lists its stored ones. When the player has the match choice, it follows as two round radio buttons, Any and Exactly this. Last is every other component as text in vanilla's `/give` syntax, `[unbreakable={},!food]`. The box's hint is a short example, and its tooltip explains the syntax. Vanilla's own item parser reads the text, and it is checked as `/give` checks a stack. While it is not valid it shows red with vanilla's error under it, and nothing is written.

Changes are written as they are made. Done keeps them, and Cancel and Escape write back the value from before the dialog opened. The value is a setting, never the player's item. The dialog's slots are not real slots, nothing touches the inventory or a container, and nothing is sent to the server, so the picker belongs to MenuKit, not a slot library. With no world open (a settings screen on the title screen) the picker uses vanilla's own data, loaded once.

## Widget host

A `WidgetHost` puts a vanilla-style widget (anything that is a `GuiEventListener` and a `Renderable`) in a panel, at the element's box. It is the one way MenuKit hosts a vanilla widget. `TextField` and `Slider` are built on it, and a mod hosts a widget another library hands it the same way (see [recipes](recipes.md#host-a-widget-another-library-made)). `WidgetHost.builder().widget(supplier).size(w, h)` builds one. Call `widget` first, since it sets the type `place` works with. The supplier runs when the widget is first needed, at the screen's init.

Every frame the host moves the widget to its box and draws it there. A vanilla `LayoutElement` is moved with `setX` and `setY`, and an `AbstractWidget` is also given the box's width and height. Anything else is moved by `place((widget, x, y, width, height) -> ...)`, which also wins over the `LayoutElement` path when given. Building a host whose widget MenuKit cannot move, with no `place`, fails at the first screen open with a message saying so. The widget is clipped to its box and to any scroll area it sits in.

The host routes the mouse itself, in screen coordinates, the way vanilla routes it to a screen's widgets: the click (with vanilla's double click and the modifier keys held), the drag while the press is held, the release of that press, and the wheel. A hosted widget therefore takes clicks on a standalone screen and on a panel over a vanilla screen alike. A click the widget takes gives it keyboard focus. Keys, typed characters, Tab and arrow focus and narration come through vanilla's focus, as for `Button`. A hosted widget that stops being drawn, or is disabled, gives up focus at the next key and Tab skips it.

`overflow()` is for a widget that draws past its box while it has focus, such as a dropdown's open list. While it has focus it draws unclipped on top of every panel on the screen, after the dialogs, and takes clicks anywhere until a click it does not take ends its focus. Under a dialog it does not belong to, it draws in place.

A hosted widget follows the rules of any element. Under another panel's claim it takes no click and shows no hover. Disabled, it takes no input. Its look is its own: it draws itself the same in both looks.

## Color field

A `ColorField` is a color setting: a swatch of the color and a lens onto it (`state(IntSupplier, IntConsumer)`). The value is `0xRRGGBB`, or `0xAARRGGBB` with `alpha(true)`. Without alpha the value's top byte is ignored when read and written as zero. `label(text)` names it for the dialog's title and the narrator.

A click on the swatch (or Enter on it) opens a modal dialog on the same screen, in its kind. The Basic tab comes first. It shows the 16 vanilla dye colors in rainbow order, two rows of six with the four neutrals centered under them. Each is shown by its dye item and named in a tooltip by vanilla's color name (Light Blue), and the current one is ringed. A dye is opaque, so picking one writes alpha `FF`. The Custom tab has a saturation and brightness square, a hue bar, a transparency bar over a checkerboard when there is alpha, the color before and now side by side, and a hex field. Typing in the hex field is free, and only valid hex is written: `#RRGGBB`, and with alpha also `#AARRGGBB`, where six digits keep the current transparency. While the text is not valid it shows red, and when the field loses focus it goes back to the color's hex. `ColorField.parseHex` and `formatHex` read and write the same strings. The dialog is as wide and as tall as the shown tab, so it grows when the player switches to Custom and shrinks back on Basic.

Each change is written through the lens as it is made, so the screen behind the dialog shows it at once. Done closes the dialog and keeps the change. Cancel and Escape write back the color from before the dialog opened. The dialog needs a screen, so a color field on the HUD only shows its swatch.

## Input context

Every input method receives an `InputContext`, as `render` receives a `RenderContext`. It carries the content origin, the mouse, whether the element's surroundings are disabled, and the kind of screen. No element caches its origin or its hover state from the last frame. A container hands its children a context moved to their origin through `ChildDispatch`, the one dispatch every host and container uses. An open overlay (a dropdown's list) takes a click first, then the first child whose hit test contains the point.

## Structure does not change after build

`build()` freezes the panel's element list. No method adds an element to a built panel. Visibility, position, and supplier-driven content change at runtime. To change the element list, build a new panel. The one element whose children change while the screen is open is `ListView` (Live lists, below).

A hidden element or panel is inert on every surface. It does not render, receive clicks or show a tooltip. It takes no room in a panel's layout or a `Flow`. `Row` and `Column` place once, so a hidden element there keeps its gap.

## Size

Width flows down from the panel to its elements. A label wraps to it and a slider caps to it. Height flows down only to an element whose `fillsHeight()` returns true. Through `fillHeight(int)`, that element gets the room from its top edge to the bottom of the panel's viewport. The viewport is the panel's pinned height or, for a screen's MAIN panel, the screen's height. With no viewport the element gets -1 and takes its natural height.

Three built-in elements fill. A `Tabs` with no fixed size does. `ScrollContainer.builder().fillHeight()` (7.3.0) takes the height it is given and scrolls its content in it; with none given it is its declared height, or as tall as its content. A vertical `Flow` holding a filling child fills too, and gives that child what is left after its other children and gaps, so a header and a row of buttons sit above a list that takes the rest. A panel gives a filling element the room from its top edge down, so put what goes under it in a vertical `Flow` with it.

A `Tabs` page is handed to a body that fills (7.3.0). The page then does not scroll the body as a whole: the filling element gets the page's height from its top edge down to the band's bottom inset and scrolls itself, so the header above it stays put. The page's inset, band and separators are the same as for any body, and a `ScrollContainer` on the page draws no band of its own (`PanelElement.inBand`). A body with nothing filling scrolls as a whole, as before. The same page looks and works the same as a standalone screen's main panel.

## Live lists

A `ListView` (7.3.0) shows one row element per item of a list the mod owns, and follows it while the screen is open. `items(supplier)` is read every frame, `key(function)` gives each item a stable identity, and `row(factory)` makes a row for a key the first time it appears. A new key's row is attached to the screen at once, exactly as an element present when the screen opened (a `TextField` makes its text box, a button joins the keyboard's focus order). A key that goes has its row detached: keyboard focus it held is let go and an open popover in it closes. A key that stays keeps its row, the same object, so a rename in progress keeps its text and focus while the data refreshes. Rows are in the order of `items()`, stacked top to bottom `gap` apart, each as wide as the list. A row is any element MenuKit can place, usually a boxed `Flow`. It is built once, so it reads what can change through suppliers, by key.

The list's height is its rows', read every frame. A list longer than its room goes in a `ScrollContainer`, usually one that fills (Size). A list in the middle of a page pushes what is below it: its whole height, the toolbar it draws included, is its `extraLayoutHeight()`, so the elements after it are placed as if it took no room, as after a closed `Section`, and move down as rows are added or grow and up as they go, in the same frame. That holds on a panel, on a `Tabs` page with or without a filling element, in a `Section`, through a `Column` or `Row`, below a vertical `Flow` holding the list, and in a `ScrollContainer`, whose scroll range follows in the same frame. Scrolled down, a list above the view that grows or shrinks moves the scroll by as much, so what is on screen stays put. A `ScrollContainer` built with `fitHeight()`, as tall as its content up to its declared height, pushes what is below it the same way, its whole height its `extraLayoutHeight()`: place what follows it as if it took no room.

`selection(get, set)` is a lens onto one selected key. A click on a row where none of its controls takes the click selects it, and the selected row is marked (List editing, below). After a click in the list, Up and Down move the selection, except while a text field has the keyboard. When the selection changes other than by a click, by the mod's code or the arrow keys, the scroll area around the list scrolls the least distance that shows the selected row (`PanelElement.takeRevealRequest`). A selected key whose item is gone clears the selection through the setter. `empty(element)` shows in the list's place while there are no items.

The attach and detach path is shared: `Attachment` remembers the screen a container's children are attached to, so any container that adds a child after build attaches it the way the screen's init does.

## List editing

Every editing option is optional, and a list with none of them is the list above, exactly. The data stays the mod's: the list only calls back and shows what `items()` returns next, so an add or move the mod refuses changes nothing.

The options share one toolbar, `list.toolbar()`, an ordinary element the mod places above the list's scroll area so it stays put while the rows scroll. Left to right it holds the search field (`search(item -> text)`), taking the free width; the sort picker and its direction (two or more `sort(label, comparator)`, the first the default, `sortState(get, set)` to remember the choice); one add button per `add(label, action)`, with a hover tooltip saying what the kind is given as `add(label, tooltip, action)`; then `- Remove item` (`remove(key -> ...)`, its label overridable with `remove(label, ...)`, and its tooltip with `remove(label, tooltip, ...)`) and up and down arrows (`move((key, toIndex) -> ...)`). Remove and the arrows act on the selected row, and a click anywhere in a row selects it; without `selection(get, set)` the list keeps its own. They are gray while nothing is selected or the row can't do it: a `pinned(predicate)` row, up on the top row and down on the bottom one, a move past a pinned row, remove on a row a search hides, and either arrow while a query is typed. `confirmRemove(item -> body)` asks first in a `ConfirmDialog` whose body names the item. After a remove, the row that took its place is selected (the one before it when it was last), so repeated removes are quick. Alt+Up and Alt+Down move the selected row. An added row is scrolled into view, clearing a query that hides it. A list can't both sort and move: `build()` throws. The toolbar lines up with the edges of whatever it is laid out in: placed by the mod it is as wide as its container gives it, like any other element, so in a column with a scroll area its right end is the scroll area's outer edge, level with the controls above it. A list whose toolbar is never asked for draws it at its own top, as wide as the rows, inside the band and clear of the scrollbar. `title(component)`, or `title(() -> component)` read every frame for a live count, puts the list's heading on the toolbar's line at its left edge, so the heading and the buttons share one line: drawn in the look's heading style, centered on the buttons, before the search field (which then takes the width between them) or empty room, its styles kept (a gray count stays gray), and cut with "..." if it would reach the search field or the first button, shown whole while hovered. `title(title, tooltip)` gives it a hover tooltip of its own instead, fixed or read while hovered, shown cut or not, as a `Section` with a tooltip does. A list with a title and nothing else still has the title's line; without one the toolbar is unchanged.

For a short list where each row is its own thing to edit, such as a config list of text fields, `controlsInRows()` puts up, down and a remove cross in every row instead, after a thin divider line: inside a card, on a `Section`'s header line, or beside a bare row. No selection is needed. Add stays in the toolbar.

`addDisabledWhen(condition)` grays the add buttons and `removeDisabledWhen(condition)` grays the remove, the toolbar's `- Remove item` and every row's cross alike, while the condition holds, read every frame: a list at its longest or shortest. A click on a grayed one does nothing.

`disabledReason(text)` shows above the rows while the list's `disabledWhen` holds.

The selected row reads in both looks: a white outline in the Default look (gray while the list doesn't have the keyboard), and in the Panel look a card washed lighter inside its border (a row that isn't a card keeps the outline).

A row's own content is the mod's, and the list draws nothing in it beyond the selection and, with `controlsInRows()`, its controls. A mod's own controls in a row (a toggle, an Edit button) sit at the row's right end when a `Flow.spacer()` comes before them, and `crossAlign(CrossAlign.CENTER)` centers the row's labels on their line; any other placement is the row's own `Flow` layout.

## Edit dialog

An `EditDialog` (7.3.0) is a modal dialog for settings that take effect only on Save: a title, the mod's controls, Cancel and Save, laid out as every MenuKit dialog and as wide as its content. It is built and shown like a `ConfirmDialog`, a `Panel` whose visibility reads the mod's state. Its controls are lenses onto a draft, a copy the mod fills when it opens the dialog, so nothing changes behind it while the player edits. `onSave` writes the draft back and closes it; `onCancel`, which Escape also runs, just closes it. A mod opens it from any button of its own, such as an Edit button in a list row.

## Menu button

A `MenuButton` (7.3.0) is a button that opens a menu of actions: `action(label, runnable)` for each row, `danger(label, runnable)` for one that destroys something, drawn red. A click on a row runs it and closes the menu. The menu is as wide as its widest label and, when wider than the button, ends at the button's right edge, so a small button at the end of a row opens back over the row. It is a dropdown's popover: it draws above everything around it, is not cut off by a scroll area, closes on a click outside it, and Up, Down, Enter and Escape work while it is open. A `Dropdown` can also take its options from a supplier (`items(() -> list)`), for options that change while the screen is open.

## Text field

A `TextField` is vanilla's text box with a lens onto the mod's text. `onSubmit` runs on Enter. Escape on a focused field (7.3.0) cancels the edit: the text goes back to what it was when the field took focus, written through the lens, the field lets go of the keyboard, `onCancel` runs, and the screen stays open. A second Escape is the screen's. `focus()` gives the field the keyboard from code, for a rename field that appears when its button is clicked.

## Tabs

`Tabs` is a tab strip and the area below it that shows the selected tab's body. One element holds both, so the body's top edge follows the strip's height. Each tab has a string id, a label, a body, and an optional `visibleWhen`. A body is a list of elements positioned from the body's top-left. It is laid out to the body width the way a panel lays out its own elements, and scrolls when it is taller than the body area. With no fixed size and no viewport to fill, a `Tabs` is as tall as its tallest tab, so switching never resizes it. `fitShownTab()` instead makes it as wide and as tall as the shown tab, for a dialog that should fit what it shows.

Selection is consumer state. `state(get, set)` reads the selected id every frame and writes the id the player picks. To select a tab from outside, the mod writes its own field. When the selected tab is hidden, the next visible tab is shown, or else the previous one. Nothing is written, so the hidden tab takes the selection back when it reappears.

`Tabs` has three modes. `WRAP` breaks the strip into the fewest rows the width allows and splits the tabs so the rows are about equally full. A tab keeps its row and place when another is selected. `SIDE_SCROLL` keeps one row. When it overflows, it scrolls from the left with arrows at both ends, and a newly selected tab slides into view. `SIDEBAR` puts the tabs in a column down the left with the body to its right. The selected tab reaches further left and opens into the body. The column is as wide as its widest label, at most a third of the element. When the tabs are taller than the column, a scrollbar runs down its left edge. It is a `ScrollContainer`'s scrollbar, with the same track and handle at the same size. Drag the handle, or click the track to jump there. A newly selected tab slides into view. The tabs narrow to make room for the bar, so the body does not move. Both strips scroll the way a `ScrollContainer` scrolls its content. They move by pixels, 10 per wheel notch, at once under the wheel and the handle. An arrow slides the row one tab along. A selected tab that is partly off the strip slides into view instead of jumping. `sidebarHeader(elements...)` puts elements above the column, such as a Back button, in the column's width. The body beside the column still starts at the top. On a container screen the sidebar is drawn in vanilla's tab colors. Resource packs that restyle vanilla's tabs change the top strip there but not the sidebar.

In the Default look (see Looks), the strip of `WRAP` and `SIDE_SCROLL` is Create World's tab bar. Every label is white, and the selected one is underlined and open into the page below. The page is vanilla's list background down to a separator at the bottom. `SIDEBAR` there is the same tab bar turned on its side. Vanilla's tab sprites are turned a quarter and open toward the body on the right. The selected one opens into a page of the list background that runs from the column's edge to the element's right. Vanilla's separator runs down the column's edge above and below the tabs. Labels stay upright, white, the selected one underlined. Either page insets the body like the list band, `DEFAULT_INSET_X` from its sides and `DEFAULT_INSET_Y` above and below (in a dialog, `DIALOG_INSET` each way). Sizes, arrows and behavior are the same in both looks. The sidebar's scrollbar is vanilla's thin list scroller there, as a `ScrollContainer`'s is.

`header(elements...)` puts a row across the whole element, above the strip or the sidebar column and above the body, in every mode. It is a menu's own title bar. Its elements get the element's full width, so a `Flow` with a spacer at each end centers a label across it. The strip, the column (with its `sidebarHeader`) and the body start under it after a 4 pixel gap, and the body is that much shorter. The screen's title is separate. A screen whose header names it can call `hideTitle()` so the name shows once.

`tabColumn(false)`, in `SIDEBAR` only, draws no tab column. The column is 0 wide, so the body takes the whole width of the same page the column would sit beside. In the Default look that is the same darker band, the same insets, bottom separator and scrollbar, so a menu with a single page looks like its tabbed siblings without the column. In the Panel look the body starts at the left edge. `header(...)` still runs across the top, and clicks where the column would be reach the body. The selected tab is the one shown, so with several tabs the `state` lens still chooses which. It cannot be combined with `sidebarHeader(...)`, which lives in the column. Put those elements in `header(...)` instead.

`align(...)` is `LEFT`, `CENTER`, `RIGHT`, or `FILL`, applied per row. In `SIDEBAR` it places each label in its tab, with `FILL` the same as `LEFT`, and labels stay put when the selection changes. `FILL` gives every tab in a row, the last row included, its label width plus an equal share of the leftover space. In `SIDE_SCROLL`, alignment applies only while the row fits. A label wider than its tab is cut short, ending in three dots, and shows in full on hover.

A tab can have an icon left of its label. `icon(texture, textureSize, drawSize)` takes a supplier of a standalone square texture's id, such as a mod's icon read from its jar into a `DynamicTexture`, and its side in texels. The whole texture is drawn shrunk to `drawSize` pixels square. `icon(sprite, drawSize)` takes a GUI sprite instead. The tab is wider by the icon and `ICON_LABEL_GAP` (4 pixels), so the icon never covers the label or cuts it shorter. The icon and label are placed together: centered as one in a strip tab, and aligned as one in a sidebar tab, so a label with an icon starts further right. The selected tab's underline in the Default look stays under the label. A supplier that returns null draws nothing but keeps the room, so the tab does not change width while its texture loads. A tab with no icon is drawn exactly as before. `Icon.builder().texture(id, textureSize)` draws a texture the same way as a standalone element.

By default `Tabs` fills its panel's width and height. Put it in a screen's MAIN panel for a full-screen tabbed menu. `size(width, height)` fixes both, for a panel that has no height to give it. Each tab keeps its body's scroll position while the element exists. `bodyScroll(get, set)` hands it to the consumer in pixels from the top, keyed by tab id. That is the unit `ScrollContainer.state` uses. `get` is read every frame (null is the top), and `set` gets each change. A screen rebuilt on the same lens opens each body where it was, on the first frame, without sliding from the top. An offset past the body's end is clamped. The selected tab is already the consumer's through `state(get, set)`.

A body's scroll stays where the player put it. It is stored as pixels from the top. When the body changes height (a section opening or closing, a label rewrapping, a dropdown's label growing a line), what is on screen stays put. It moves only when the end of the body comes up past it. A dropdown's popover draws over the body and never changes its height. A click on a control never scrolls the body, and a body never slides. Only a strip slides. A body that stops scrolling because everything fits is at the top, and starts from the top when it next scrolls. A panel's own auto-scroll behaves the same.

Other mods can add tabs to a menu that has a name. The owner names it with `menu(id)` on the builder, and another mod calls `Tabs.addTo(id, tab)` at its init. An added tab's body is a factory, `body(() -> elements)`. It is built every time the owner builds the menu, against the adding mod's own config. The owner's builder order is the menu's order. An owner tab marked `standIn()` holds a place for a tab another mod may add. An added tab with the same id takes its place. With nothing to replace it, the stand-in shows with a dimmed label. Only the place carries over. The replacement keeps its own `visibleWhen`, or always shows, so an owner's switch that hides its stand-ins never hides the real tabs. Any other added tab places itself with `after(id)` or `before(id)`, or goes at the end. Added tabs that share a place are ordered by id, so the result does not depend on which mod loaded first. When two mods add the same id to one menu, the second `addTo` is refused. A tab added to a menu that no mod builds is never shown.

## Section

`Section.builder(title)` is a collapsible section. Its header row has an arrow, an optional color swatch, the title, and a gray summary read every frame. `Section.builder(() -> title)` and `swatch(() -> argb)` (7.3.0) read the title and swatch every frame too, so a section built once, such as a `ListView` row, shows a rename or a recolor in place. Clicking the header opens and closes it. Its children are positioned from the top-left of the content area under the header and laid out to the section's width. They get clicks, keys and overlays as they do directly on the panel. A closed section's children are not drawn and get no input except mouse releases.

Position the row after a section where it sits while the section is closed. When it opens, the panel's reflow pushes later rows down by the content's height and the scroll height follows, the same way a wrapped `Flow` pushes rows. Sections nest. Open state is the element's view state and starts closed. `open(true)` starts it open, and `state(get, set)` hands it to the consumer. A disabled section grays its header and everything in it. In the Default look the header takes the Controls screen's category header colors, with the title in white. It still reads from the left as in the Panel look, in line with the content under it.

## Layout helpers

`Row` and `Column` compute positions once and return a `List<PanelElement>`. They do not exist at runtime. The positions are computed on the panel's first layout pass, when the game's font can measure text. A panel or dialog laid out with them can therefore be built at mod init. An element enters a layout built: `.add(Button.builder()...build())`, and the helper moves it into place. A custom element that can only be constructed once its position is known implements `ElementSpec`. `.build()` returns positioned elements that go into a panel with `.add(...)` or `.elements(...)`.

`Flow` is the runtime row. Its children flow left to right at the panel's width and wrap to new rows. `Flow.spacer()` takes whatever a row's other children leave of that width. A label, a spacer and a control make a settings row with the control pinned to the right edge at any window width, with no width written anywhere. A spacer at each end of a row centers what is between them. When the row wraps, the control drops under its label. A row top-aligns its children. `crossAlign(CrossAlign.CENTER)` (7.3.0) centers each on its row's line instead, so a label sits level with the middle of a taller control and controls of different heights line up, with no pixel offsets; `CrossAlign.END` sets them on the line's bottom. The line is the tallest child's first line, so an open `Section` in the row keeps its header on it and grows downward.

`Flow.builder().boxed()` draws a card behind the children, for a row of a list that reads as one unit (a world in a world list). The children sit `Flow.BOX_PADDING` (6) inside the card. A boxed row fills the width its panel gives it, and its height hugs its rows plus the padding. In the Default look the card is a dark translucent box with a one-pixel light border that brightens while hovered. In the Panel look it is the `INSET` panel style. An icon beside a stack of lines is a boxed Flow holding the icon and a vertical Flow.

`Flow.builder().vertical()` is the runtime column. Children flow top to bottom and wrap into a new column to the right. It wraps at the frame band, which is the room from the Flow's top down to the bottom of the screen's frame beside its panel (a container screen's `topPos + imageHeight`). The host hands the band to the panel the way it hands it its width, and the panel hands it to its elements. A panel has a band when it is in a side region (`LEFT_ALIGN_*`, `RIGHT_ALIGN_*`) on a container screen, on an anchor on a container screen, or beside a standalone screen's main panel. On an anchor the band still runs to the container screen's frame, not the anchor's box. Anywhere else the Flow is one column. The band is not where the panel scrolls. The panel still scrolls at the screen's edge. In a column, `gap(horizontal, vertical)` is the gap between columns and the gap between children, and a spacer takes no room. In either direction a hidden child takes no room, so the Flow reflows when one hides.

`Row.width(px)` declares the row's overall pixel budget. `.addSpacer()` adds a flexible gap that expands to fill whatever the other children and spacing leave over. One thing then pins to the row's left edge and another to its right (`Back .... Reset`). Several spacers split the leftover evenly, with the odd pixel going to the last one. `addSpacer()` without `width(px)` throws, since a spacer with nothing to expand into is a mistake in the layout.

## Mode scope

Every declaration that says where a panel goes picks the game mode it is for (7.4.0): `ModeScope.SURVIVAL`, `ModeScope.CREATIVE`, or `ModeScope.BOTH`. There is no default. `CREATIVE` is a player with infinite materials (`Player.hasInfiniteMaterials()`, the switch vanilla reads), `SURVIVAL` every other player, adventure and spectator included. A container a creative player opens is `CREATIVE`. `ModeScope.of(player)` says which a player is in, `SURVIVAL` or `CREATIVE`, never `BOTH`, and `scope.includes(player)` whether a scope covers it.

The mode is read where it is used, every frame, never kept from when a screen opened, so `/gamemode` with a screen open takes effect on the next frame. With no player (the title screen, a world loading) there is no mode: `ModeScope.of(null)` is `null`, `includes(null)` holds only for `BOTH`, and only `BOTH` declarations apply.

`ModeScope` is a plain value in MenuKit's common code, not its client half, so a library that judges on the server (SlotKit's slot declarations per mode) uses the same type. It does nothing on its own. MenuKit reads it on the client.

The scoped forms are `Panel.Builder.in(scope, placement)`, `HudPanel.builder(id, scope)`, and `ContainerRegion.section(id, scope)`. The 7.3.0 forms with no scope (`position(...)`, `HudPanel.builder(id)`, `AnchorPanelAdapter.on(...)`, `OwnHost.add(panel, position, padding)`) keep working, mean `BOTH`, and are deprecated ([upgrading](upgrading-7.md#to-740)). A panel that declares no placement at all, a nested one, a dialog or a standalone screen's default stack, is `BOTH` by nature.

A screen's targeting is not per frame: `ScreenMatcher.where(test)` is asked once, as the screen opens, and a creative tab switch does not ask it again. Decide what changes while a screen is open with the mode scope or `visibleWhen(...)`.

## Placement

Where a panel sits is declared once, on the panel, for each mode it shows in: `Panel.builder(id).in(ModeScope, Placement)`, once per scope. Every host reads it. An adapter only says which screens the panel appears on. Each frame the panel takes the current mode's placement, else its `BOTH` one; with neither it does not show in that mode. The two modes' placements can be entirely different, a screen region in one and beside an anchor in the other, and `Panel.placements()` lists them. `getPosition()` is the position in effect now.

A `Placement` is what the panel is placed against and its position there:

| Placement | Against |
|---|---|
| `Placement.screen(PanelPosition)` | The host's own reference: the menu frame, the screen, the game window or the hotbar, a standalone screen's main panel. |
| `Placement.around(Anchor, PanelPosition)` | The regions around an anchor's box, stacking with the anchor's other panels. |
| `Placement.at(Anchor, dx, dy)` | The anchor's box's top-left plus the offset, at the panel's natural size. It does not stack, gets no room budget and is not kept on the screen: two panels at one spot overlap, and a negative offset goes left of or above the box. |

A placement on an anchor shows wherever that anchor's box is on the open screen, so the box is its presence. A screen adapter puts a panel's screen placements in the screen's host and each anchored one in its anchor's host on the screens it targets; an `AnchorPanelAdapter` needs no targeting when the placements name their anchors. An `AnchorPanelAdapter` has no screen of its own to place against, so a `Placement.screen(...)` on its panel, without the deprecated `on(...)`, throws at the first screen open, naming the panel and the mode. The HUD, an `MKScreen` and a library's own screen (`OwnHost.add(panel, padding)`, which reads the panel's placements) place against their own reference only, and reject an anchored placement at registration.

`in` and the deprecated `position(...)` don't mix on one panel, and each scope is declared once; either mistake throws at build. A screen has one `main()` panel in each mode. In each of survival and creative, each panel shows its placement for that mode, else its `BOTH` one; two panels that would both show a main in the same mode throw at registration, and the error names both panels and the mode. So two `BOTH` mains clash, and so does a `BOTH` main beside another panel's `SURVIVAL` main, unless the `BOTH` main's panel has a survival placement of its own that isn't a main. A survival main on one panel and a creative main on another are fine, and so is one panel with a `BOTH` main and a main for one mode.

A slot placed beside another slot, per mode, is SlotKit's to declare, with the same `ModeScope` ([SlotKit's concepts](https://github.com/trevorschoeny/slotkit/blob/main/docs/concepts.md#address)).

`Panel.Builder.fixed()` says the player can't move the panel ([moving panels](#moving-panels)).

The positions:

| Placement | Where |
|---|---|
| `PanelPosition.main()` | A standalone screen's frame, centered. One per screen. |
| `PanelPosition.region(OutsideRegion)` | Outside the host's reference rectangle, along one of its edges. |
| `PanelPosition.screenAnchor(InsideRegion)` | On one of nine spots of the screen or game window, inset from the edges it touches. |
| `PanelPosition.center()` | Centered on the screen as an overlay, drawn on top. |
| `PanelPosition.pixel(Supplier<ScreenOrigin>)` | At an absolute origin re-evaluated each frame. Returning `null` skips the frame. It does not stack and does not wrap. |

Any placement takes two modifiers. `.priority(n)` orders panels that share a region (lower sits nearer the anchor edge) and is the z-order within a host (lower draws underneath). The default is 100. Ties go by the registering mod's id, then by registration order, so the order is the same on every launch. `.offset(dx, dy)` nudges one panel after it is placed, and its siblings stack on its un-nudged position.

The two placements that stack, `region(...)` and `screenAnchor(...)`, take a third: `.gap(n)`, the space in pixels before this panel. In a region that is the space between the panel and the reference on the side the region sits, and between the panel and the sibling before it in the stack. `region(RIGHT_ALIGN_TOP).gap(0)` sits flush against the frame's right edge, and a second panel there with `gap(0)` sits flush under the first. On a screen spot it is the space between the panel and the sibling before it; the first panel on a spot keeps the edge inset. Without `.gap(n)` each host keeps its own spacing: 2 pixels in every region (container screens, anchors, the HUD's hotbar, a standalone screen's main panel), and on a screen spot 4 pixels on a vanilla screen and 2 on the HUD. The gap belongs to the panel that declares it: the space after a panel is the next panel's gap, not its own. A negative gap throws when the position is built; to overlap a neighbor, use `.offset(dx, dy)`.

A panel with no placement is unplaced. An adapter or the HUD rejects it at registration, naming the panel. `MKScreen` and a custom menu's screen give it a default instead. The first unplaced panel becomes `main()`, and each later one stacks below it.

A panel wraps its width to the space its placement leaves and scrolls its height when taller than its room. `Panel.size(w, h)`, `pinnedWidth(w)`, and `pinnedHeight(h)` override this.

On a standalone screen, the `main()` panel makes room for the `region(...)` panels around it. Its room leaves out the height of the panels above and below it and the width of the panels beside it, gaps included. A panel above a full-height menu still fits, and the menu gets a little shorter. A main panel with room to spare stays centered.

## Shared panels

Mods that deliberately work together can put their elements in one panel (7.4.0). A shared panel is named by an id that belongs to no single mod, a plain string such as `trevlar:gear`, with no registry. Each mod joins it from its client initializer with `SharedPanels.join(id, contribution)`. No mod creates the panel and no mod depends on another. Unrelated mods that happen to share a spot don't need this: panels in one region already stack.

A `Contribution` is one mod's part: its elements (`add(...)`), an order number and a mode scope (`Contribution.builder(order, scope)`), and its own `visibleWhen(...)`. It is a list of elements, not a layout of its own. It also carries the panel's own declaration: its placement per mode (`in(scope, placement)`, at least one), its `style(...)`, its axis (`vertical()`, a row by default), its `gap(px)` (`Flow`'s default; `0` keeps slots on vanilla's 18 pixel pitch) and whether it is `fixed()`. Every contribution carries the whole declaration, so whichever mods are installed can build the panel.

MenuKit builds each shared panel once, at client start, after every client entrypoint has run and before declarations freeze, from whatever contributions joined. A `join` after that throws. The panel's id is the shared id.

- **One flow.** The contributions are laid out in one `Flow` along the panel's axis, by order number, ties by mod id, so the result doesn't depend on load order. A contribution out of its mode scope, whose `visibleWhen` is false, or whose elements are all hidden, takes no room: the next one moves into its place, with no stray gap.
- **All hidden.** With every contribution hidden, by any of those, the panel isn't placed, so it draws nothing, not even an empty frame, and claims nothing.
- **Disagreement.** If contributions declare the panel differently (placements, style, axis, gap or `fixed()`), the lowest order's declaration is used and MenuKit logs a warning naming both mods. Nothing crashes, so a player with mismatched versions still gets a panel. A `pixel(...)` origin is a lambda, and two lambdas can't be compared, so two placements that differ only there count as the same.
- **One mod installed.** The panel is that mod's contribution alone, an ordinary panel. With no contribution there is no panel.
- **Registration.** It goes where an ordinary panel with the same placements would. With a screen placement it shows on every container screen, chests and furnaces as well as the inventory, since no contribution says which screens; it goes through a screen adapter, which puts its anchored placements in their anchors' hosts there. To keep a shared panel to the screens an anchor is on, give it only anchored placements. With only anchored placements it goes through an `AnchorPanelAdapter`, on any screen where the anchor is. In a shared region it is credited to the mod whose declaration won.

## Moving panels

Players can move panels themselves (7.4.0). Mods have nothing to do: every panel can be moved unless it says otherwise.

- **The key.** "Move panels", in MenuKit's category of the Controls screen, is unbound until the player binds it. On a screen it turns edit mode on and off. In game, with no screen open, it opens a clear screen over the HUD where HUD panels can be moved.
- **Edit mode.** Every panel the player can move gets an outline, and a hint line sits at the top of the screen. Nothing else on the screen takes a click: not the panels' elements, vanilla's slots or another mod's widgets. Keys reach the screen as usual, except Esc and the key, which both leave edit mode. Esc doesn't also close the screen. Edit mode ends with its screen: a screen that closes while editing (the inventory key, the server closing the container, another screen opening) drops a drag in progress unsaved, and the screen shown again is not in edit mode. The key does nothing while a text field on the screen has the keyboard, or while the Controls screen waits for a key to bind, so it can be typed and bound.
- **Moving.** Drag a panel to move it. A plain drop places it in both game modes; with Shift held at the drop, only in the current one. A right-click puts the panel back where its mod declared it, in both modes.
- **Where it lands.** The place is kept on each axis from the third of the screen the panel is nearest (its start edge, its center or its end edge), so a panel dropped by the right edge stays by it when the window is resized or the GUI scale changes. It is kept in `config/menukit/panel-positions.json`, by panel id and game mode. An entry MenuKit can't read is skipped and the others kept; a file that isn't JSON at all is moved to `panel-positions.json.corrupt`, so it isn't lost, and every panel starts where its mod put it. A file that can't be read at all (locked, or without permission) is left where it is, every panel starts where its mod put it, and moves aren't saved until the next start.
- **What a move changes.** Where the panel sits, not whether it shows. A moved panel still shows only where its declaration would place it: its screen targeted, its anchor present, its own `visibleWhen`. It leaves its region's flow, so the panels after it close up.

To keep a panel where you put it, mark it `fixed()`. Use it for a panel whose place is part of what it means, such as one lined up against vanilla's own art:

```java
Panel tabs = Panel.builder("mymod:tab_strip")
        .in(ModeScope.BOTH, Placement.screen(PanelPosition.region(OutsideRegion.TOP_ALIGN_LEFT)))
        .fixed()
        .add(tabStrip)
        .build();
```

`HudPanel.Builder.fixed()` does the same for a HUD panel, and `Contribution.Builder.fixed()` for a shared panel, where the winning declaration decides. `Panel.isFixed()` reads it back. Some panels are never movable, `fixed()` or not: background panels (the container region's two included), overlays (centered, dimming or modal, which every MenuKit dialog is), popovers, and a standalone screen's `main()` panel. The cycle strip is fixed, since it draws from the window's size rather than from where it is placed.

A player's position is stored under the panel's id, and a shared panel's under its shared id, so moving it moves every mod's part together. Ids key across every mod the player has, so namespace them: `mymod:elytra`, not `elytra`. Two panels with one id share one position.

## Reference

A reference is the rectangle a `region(...)` placement is measured against. It is not the panel and has no relation to the panel's size. The host decides it. It is a container screen's frame (extended by its chrome, such as creative's tab rows or an open recipe book), an anchor's box, a standalone screen's main panel, or on the HUD the vanilla hotbar. `Reference` is the record that carries it. A region never names its reference.

## Region

A region names where a panel sits relative to its reference. There are two enums, one for each side of the reference's edge:

| Type | Placement | Values |
|---|---|---|
| `OutsideRegion` | Outside the reference, along one of its edges | `LEFT_ALIGN_TOP`, `LEFT_ALIGN_BOTTOM`, `RIGHT_ALIGN_TOP`, `RIGHT_ALIGN_BOTTOM`, `TOP_ALIGN_LEFT`, `TOP_ALIGN_RIGHT`, `BOTTOM_ALIGN_LEFT`, `BOTTOM_ALIGN_RIGHT`, `TOP_CENTER`, `BOTTOM_CENTER`, `LEFT_CENTER`, `RIGHT_CENTER`, `CENTER` |
| `InsideRegion` | On the screen, at one of nine spots | `TOP_LEFT`, `TOP_CENTER`, `TOP_RIGHT`, `LEFT_CENTER`, `RIGHT_CENTER`, `BOTTOM_LEFT`, `BOTTOM_CENTER`, `BOTTOM_RIGHT`, `CENTER` |

Each side of the reference has three regions: aligned to its start, centered on it, and aligned to its end. `TOP_CENTER` and `BOTTOM_CENTER` are centered horizontally above and below the reference, and `LEFT_CENTER` and `RIGHT_CENTER` (7.4.0) vertically beside it, so a column beside an anchor's box (the armor slots, say) sits level with the box's middle. Panels in a centered region stack straight away from the reference, each one centered. `CENTER` is centered on the reference itself.

```java
// A column of toggles left of the armor slots, its middle level with theirs.
Panel toggles = Panel.builder("mymod:armor_toggles")
        .add(toggleColumn)
        .in(ModeScope.BOTH, Placement.around(ARMOR, PanelPosition.region(OutsideRegion.LEFT_CENTER)))
        .build();
new AnchorPanelAdapter(toggles);
```

Panels in the same region stack in priority order. `InsideRegion` spots resolve through one resolver with each context's inset. On the HUD and on vanilla screens the inset is 4 pixels, and `CENTER` on the HUD starts directly below the crosshair. On a standalone screen the inset is the safe-area margin for the screen's chrome. The chrome is always placed, even when it is oversized.

## Five contexts, one host each

A context answers one question: what is this panel placed against? Each context is one `PanelHost`. Every host sorts its panels, places them, draws them in layers and routes their input the same way.

| Context | Placed against | Entry type | Placements | Input |
|---|---|---|---|---|
| Container screen | The menu frame | `ScreenPanelAdapter` | region, screenAnchor, center, pixel | Yes |
| Other vanilla screen | The screen | `VanillaScreenPanelAdapter` | screenAnchor, center, pixel | Yes |
| Anchor | A rectangle a mod supplies on any screen | A placement on it (`Placement.around`, `Placement.at`), through any adapter | region, center, pixel, and `at` | Yes |
| HUD | The game window during play, and the vanilla hotbar | `HudPanel` | screenAnchor (`.region(InsideRegion)`), region around the hotbar (`.region(OutsideRegion)`), pixel | No |
| Standalone | A screen the consumer opens | `MKScreen` (subclass), or a library's own screen through `api.host.OwnHost` | main, region, screenAnchor, center, pixel | Yes |

A placement a context cannot resolve is rejected at registration. HUD panels do not receive input. For a clickable HUD control, open a standalone screen from a key binding.

Every surface draws in the same order across all its hosts. FLOW panels come first, then POPOVER panels, then a dim when any shown panel dims behind it. OVERLAY panels (those that `center()`, dim behind, or track as modal) draw on top. Within a layer, a lower host draws before an upper one: a standalone screen's own host, then the screen's adapters, then the anchors. Within a host the sorted order holds. An element renders the same in every context.

A background panel, `Panel.builder(id).background()` (7.4.0), is the other end: it is drawn as part of the screen's own background, right where the screen draws its image (after its dim, before the chest texture), so everything else on the screen draws over it: vanilla's labels and slots, every other mod's widgets and buttons, every other panel, tooltips. The slots it shows draw with it, right after its elements, over it and clipped to what it shows of them (Slot rendering), so they are under every widget too: another mod's button over one of them hides its item, and over the button the slot is not hovered. What a mod draws into the screen's own background after vanilla's image still lands over it. It is meant for a panel that takes the place of part of the screen, as the container region's two panels do, and never gets in another mod's way. A panel is background or popover, not both; asking for both throws at build.

A popover, `Panel.builder(id).popover()`, is a panel that pops up over the screen. It draws above every ordinary panel of every host, whichever registered first, and below a modal and its dim. Its placements are still its own. On a container screen, popovers draw after the ordinary panels and before the slots a slot library adds to panels (SlotKit's created slots), so a popover's own slots draw on it. Another panel's created slot under a popover still draws over it.

## Claims

What a panel covers is inert. A point on the screen is claimed by the topmost panel that takes it. Topmost follows the draw order above (OVERLAY, then POPOVER, then FLOW), so what is drawn on top takes the point:

- An opaque panel (the default) takes every point of its rectangle. Nothing inside it lets a point through to what is behind the panel.
- A see-through panel, `opaque(false)`, takes only its solid elements, meaning the shown, opaque and interactive ones, such as a button. A label on it takes nothing.
- An element's open overlay, such as a `Dropdown`'s list, takes its area whatever its panel's opacity.
- A shown modal (`tracksAsModal`) takes every point on its screen.
- A background panel (7.4.0) takes no point at all, opaque or not. It is drawn under everything on the screen, so nothing on the screen is behind it: whatever lies over it, another mod's widget included, is drawn on top and keeps the point, which is this same rule. Its own elements get input last: a click once the screen's widgets (every mod's) and every panel above have declined it, never on a slot it shows (that is vanilla's to click), and the wheel once the screen and every other handler have. Only its own slots are cut, at the edges of the clip they are shown under.

Under a claim, vanilla gets nothing. There is no slot highlight, click or tooltip, no widget or list hover, and no creative tab. The claim routes the point to the claiming panel instead. A panel's own slots stay live under its own claim (a created slot it presents, or a standalone screen's own slot group). A standalone screen's own widgets stay live under its own panels too. Every surface runs the same check, so an anchored panel and a standalone screen's panels block what they cover exactly as an adapter's panel does.

Tooltips go through one MenuKit check before vanilla queues them. To hide every tooltip in the game for a time, register a condition once from client init with `MKTooltip.hideWhen(() -> ...)`. While any registered condition is true, no tooltip draws, a panel's own element tooltips included. Inventory Plus's "hold Ctrl to hide tooltips" setting uses it.

To hide one kind of tooltip, register a predicate of `MKTooltip.Kind` instead: `MKTooltip.hideWhen(kind -> kind == MKTooltip.Kind.ITEM && ...)`. A tooltip is `ITEM` when an item stack's tooltip comes through vanilla's item paths: a slot on any container screen (creative included), the recipe book, an item in chat, `setTooltipForNextFrame(font, stack, x, y)`, or lines from `Screen.getTooltipFromItem`. Everything else is `OTHER`, including a mod's item tooltip built from `ItemStack.getTooltipLines` and queued as plain lines. MenuKit marks the item paths just before they queue, and the mark goes with the next tooltip or ends with the frame, so it never reaches a later tooltip. Hiding by kind changes nothing else: a tooltip that shows is docked, wrapped, clamped and scrolled as before. Dock and Hide Tooltips' "hide item tooltips" and "hide all other tooltips" settings use it.

The same check places every tooltip, so a mod can scroll one too. `MKTooltip.onWheel((horizontal, vertical) -> ...)` receives the mouse wheel whenever it turns over a shown tooltip. It runs before any other handler, whether or not something then uses the event. `MKTooltip.scrollBy(dx, dy)` moves the tooltip on screen by that many pixels (positive y moves it down). MenuKit keeps a scrolled tooltip inside its own extent, so one that fits on screen never moves. It resets the offset when the tooltip's text changes or the tooltip goes away, and `MKTooltip.resetScroll()` resets it by hand. While a tooltip is scrolled with its top above the screen, its first line stays pinned at the top edge and the rest scrolls under it. Inventory Plus's "scroll long tooltips" setting uses it.

Two more switches on the same check keep a tooltip on screen. Both are off unless a mod registers them from client init. `MKTooltip.wrapWhen(() -> ...)` breaks any text line wider than the screen (less a 4 pixel margin and the frame's padding) onto more lines with vanilla's splitter, and keeps the tooltip inside both sides. Images such as a bundle's grid are left as they are. A wrapped first line stays one title, so the scroll pin keeps all of its lines. `MKTooltip.clampWhen(() -> ...)` keeps the tooltip's top on screen. A tooltip taller than the screen starts at its title and runs off the bottom, and `MKTooltip.scrollBy` with a negative y brings up the rest, down to its last line. Inventory Plus's "keep tooltips on screen" setting uses them.

Vanilla puts a tooltip beside the cursor, so a wide one near an inventory lands over the slots the player is reading. `MKTooltip.avoidCoverWhen(() -> ...)` docks it instead, and is also off unless a mod registers it. While it holds, a tooltip vanilla would place beside the cursor sits centered at the bottom of the screen, 4 pixels (`MKTooltip.EDGE`) above the edge. When the cursor is within 20 pixels (`MKTooltip.DOCK_MARGIN`, a bit more than a slot) of where that tooltip would sit, not only directly over it, it sits centered at the top instead. Nothing wraps or changes side. `clampWhen`, `wrapWhen` and the scroll work on a docked tooltip as on any other, so one taller than the screen starts at its title under `clampWhen`. A tooltip vanilla anchors to a widget for the keyboard stays where vanilla puts it. Inventory Plus's "keep long tooltips out of the way" setting uses it.

## Targeting

A `ScreenPanelAdapter` with no target renders on every container screen. `.on(Class...)` limits it to those screen classes and their subclasses. `.onAny()` states the default explicitly. `.onPlayerInventory()` limits it to the player inventory screen in both game modes. `.onMatching(ScreenMatcher)` takes `all()`, `allExcept(...)`, `only(...)`, or (7.3.0) `where(test)`, a test asked of each container screen as it opens, for a scope known only at runtime, such as the menus a slot group's slots were added to ([recipe](recipes.md#show-a-panel-on-the-screens-that-hold-your-slots)).

A `VanillaScreenPanelAdapter` requires `.on(Class...)` or `.onAny()`.

An `AnchorPanelAdapter` places a panel by its anchored placements (`Placement.around`, `Placement.at`): it renders in each mode on the anchor that mode's placement names, whenever that anchor's box is on the open screen, and is measured from that box. The deprecated `.on(Anchor...)` puts the panel's screen placements around each anchor it names instead. An anchor adapter whose panel names no anchor and that never called `.on(...)` fails at the first screen open.

`.onMatching(ScreenMatcher.where(test))` is decided when the screen opens. A creative tab switch keeps the same screen and does not ask again; what changes while a screen is open belongs to the mode scope or `visibleWhen(...)`.

A panel an adapter places whose elements are all hidden or empty (7.3.0), and that has no pinned size, is not placed: no empty frame, no claim. A panel of slot elements whose slots are not in the open menu is absent that way.

Adapters and HUD panels are declarations. Declare them from the mod's initializer. Constructing, targeting or unregistering one after the client starts throws, the same as every other MenuKit declaration. A panel that comes and goes at runtime keeps its adapter and gates itself with `visibleWhen(...)`. A hidden panel is not measured, takes no room in its region and claims nothing.

## Anchor

An `Anchor` is a rectangle a mod names and supplies per screen: `Anchor.of(id, screen -> box)`. MenuKit asks for the box every frame on every open screen, a container screen or not, and places the anchor's panels around it by the same region rules as the menu frame. A `null` box means the anchor is not on that screen, and its panels take no place and claim nothing. Panels on one anchor share one host and stack in its regions. Each id is declared once; a second `Anchor.of` with the same id throws. SlotKit's slot-group panels are anchors, one per slot group, and a mod can anchor to anything it can measure, such as the pause menu's button column.

The other direction needs no declaration: `Panel.placedBounds()` returns a panel's own rectangle on the current screen (or `null` when it isn't placed right now), read fresh every call. Use it to put something against a panel the mod itself made, such as a close button in its corner, with `PanelPosition.pixel(() -> ...)`.

## Slot rendering

Vanilla draws every slot, through its own `extractSlot`, so every other mod's slot hook marks a slot wherever it is drawn. What MenuKit decides is when. The rule (7.3.0): a slot a panel shows draws right after that panel, and a panel above covers the slots of the panels below it. A slot no panel shows is vanilla's, drawn where vanilla draws it, and a panel over it hides it. A panel over part of a slot hides that part and no more, and what a panel covers is inert (Claims). Menu order decides nothing, so a vanilla slot a panel shows draws on the panel, not under it.

To know which slots each panel shows before vanilla draws its slots, MenuKit lays the panels out once at the start of the frame without showing anything, and the slot elements report their slots. Vanilla's slot pass then leaves those slots out, and each panel draws its own right after its elements, with the hover highlights around the hovered one. Overlay panels do the same after the dim. A background panel (7.4.0) does the same in the screen's background pass: its slots draw right after its elements, before any widget, with the hover highlight around the hovered one (worked out by vanilla's own slot lookup at that moment), and vanilla's pass leaves them out. Vanilla's own slots no panel shows still draw after the widgets, as vanilla draws them. A library's own screen draws its own panels under every slot, as before. A slot library that does not report its slots keeps the order it had before 7.3.0: its slots draw after the panels. A slot two panels show in one frame belongs to the one on top, the one that takes clicks over both: it draws after that panel, at the place and under the clip that panel gave it. At the end of a frame, `SlotClip.panelShowing(slot)` tells a slot library why a slot was not shown: its panel was drawn (the slot scrolled out of view, so it parks) or not (the panel is hidden, so a vanilla slot it took over goes back to its own place).

A slot in a `ScrollContainer` (SlotKit's `SlotElement`) scrolls and clips like any element. A slot wholly out of view is not drawn, and its slot library parks it, so nothing hovers or clicks it. That holds at any depth (7.4.0): a row of slots inside a `Flow` inside the scroll area is skipped when it is out of view, as the scroll area's own children always were, so no slot scrolled away sits over what lies past the edge. A slot across the viewport's top or bottom edge stays where it is, so nothing beside it moves, and is cut at the edge: vanilla draws only the part inside (item, count, durability, highlight), and only that part hovers, shows its tooltip and takes a click. A click on the part past the edge does nothing, so a carried item cannot drop there. The same holds under any other clip, such as a `Tabs` body. A slot library makes this work by calling `SlotClip.shown(ctx, slot)` (in `api.host`) when an element places a slot, which hands MenuKit the clip that element draws under. SlotKit's slot elements do, so a mod that puts slots in a scrolling panel has nothing to do. `SlotClip.clipOf(slot)` (7.4.0) gives that clip back, in screen space, or `null` when nothing clips the slot, so a slot library can tell a slot cut by an edge from one wholly in view, for instance to hide a panel anchored on a slot that is cut.

`SlotRendering` draws a slot's frame and an item's outline, for elements such as `ItemDisplay` and `ItemPicker` that show an item without being a slot.

## Slot item looks

`SlotItemLooks.declare(id, look)` lets a mod say what a slot's item draws as on a container screen, per slot and per frame (Fluorite). The look is asked for every slot the screen draws with an item, vanilla's and created ones alike, and answers with an `ItemAnimation` at a point `t` between 0 and 1 (`animation.at(t)`), or `null` to leave the slot to vanilla. Only the item's own draw changes: its count and durability bar, the highlight, the tooltip and what a click does stay vanilla's. Looks are asked in id order and the first that answers draws.

- **The animation is the mod's pick.** An `ItemAnimation` draws an item at `t`. `ItemAnimation.OPEN_LID` opens a box's lid: the openness vanilla's own shulker box and chest item renderers take, so a shulker box's lid lifts and twists and a chest's, an ender chest's or a copper chest's swings up, in the resource pack's model and texture. A mod writes its own as a lambda: another stack, a sprite, the item with something over it.
- **The transform is the mod's too.** `animation.posed(t -> new ItemAnimation.Pose(scale, offsetX, offsetY))` scales the item about its box's center and moves it, at each point. An open lid stands past the 16 pixel box and draws there, so a mod that wants it inside the slot shrinks the item as it opens.
- **Timing is a `Transition`.** `Transition.of(millis, easing)` keeps, per key the mod names, which way a change is going: `toward(key, true)` plays toward 1 and holds there, `toward(key, false)` plays back toward 0, and turning mid-way goes on from where it got to. It reads vanilla's clock, so it runs whatever draws in between. Key it by something that outlives the screen (the container, not the `Slot`), and a screen opened in place of another picks a finished animation up where it stood. `Easing` has `LINEAR`, `EASE_OUT`, `EASE_IN_OUT` and `EASE_OUT_BACK`, and any function of `t` is one.

## Container region

On a container screen the player's inventory never scrolls, and everything above it can be one column that scrolls together: the chest, a box opened below it, another below that (7.4.0). That column is the container region. There is one per screen, however many mods add to it, and never a scroll area per container. Mods add **sections** to it with `ContainerRegion.section(id, scope)`, each for a mode scope (a section for `SURVIVAL` shows only in survival, read every frame): a section's `content` is any element, usually a grid of slot elements, placed where vanilla's own grid frame is, so a nine-wide grid lines up with vanilla's chest. The content is laid out to nine slots' width, `ContainerRegion.CONTENT_WIDTH` (162), so content that wraps (a horizontal `Flow`, a slot library's wrapping row of slots, a long label) wraps at nine slots. Its `title`, if it has one, is drawn above it where vanilla draws a container's. Sections stack in their `order` (ties by id), each `GAP` below the last, and a hidden one takes no room. Like an adapter, a section is on every container screen unless `on(...)` or `onMatching(...)` narrows it, and gates itself with `visibleWhen`. It also shows only while its content is visible, so content that hides itself takes its section with it: a slot library's element for a slot group that is not on the open menu, or whose slots are all hidden, shows no section with no condition of the section's own. The region is only there while one of its sections shows, and never on the player's own inventory, survival's or creative's, whatever a section's targeting says. Sections are declarations and freeze with the rest.

- **Two panels.** The region makes the screen two panels, each with its own frame: the **container list**, holding every section, and below it the **inventory panel**, around the player's inventory, 2 pixels apart (MenuKit's gap between panels on a menu). The inventory panel moves only as the list grows (below); its slots and its "Inventory" label are vanilla's, live as always, and go with it.
- **Behind everything, in nobody's way.** Both panels are background panels (Placement, Claims): drawn where the screen draws its own image, so vanilla's labels and slots, every other mod's widgets and buttons, recipe viewers, every other panel and tooltips draw over them, and claiming nothing, so another mod's button on either panel stays live and gets its clicks first, wherever it sits. The region's own slots draw with the list, right after it, so another mod's button over a slot scrolled under it hides the slot, and over the button the slot is not hovered. They are cut at the list's edges. While the region is up, the screen's background pass still runs, every mod's hook in it included, but vanilla's own container texture and the screen's title are left out: the panels and the sections' own titles are in their place. Whoever puts the region on a screen presents that screen's own grid in a section; a container slot no section shows is vanilla's and draws where vanilla's numbers put it.
- **Grow, centered, then scroll.** The container list starts as the screen's own container part, where vanilla's is, and grows with its sections. The two panels are one block, kept centered on the screen while it fits: the room left free is shared evenly above and below, so the list's top moves up and the inventory panel down by half the growth each. Where one side has less room than the other (a window too short for vanilla's own margins), that side's panel holds and the other moves until the block is centered. Only once the block is 4 pixels from the screen's top (`TOP_MARGIN`) and bottom (`BOTTOM_MARGIN`) does the list scroll. Each panel moves at most a pixel for each pixel of growth, so a box opening never makes the block jump. A resize lays it out again. It is never shorter than the screen's own container part (unless the screen is fitted, below), and neither panel moves the other way from vanilla's place, so on a tiny window it keeps vanilla's height and scrolls. While it scrolls it is wider by the scrollbar's lane, with the scrollbar inside its frame, the shared one, in the screen's look. Scrolled content clips at the list's own frame, top and bottom.
- **The screen's bounds are both panels.** The screen's `leftPos`, `topPos`, `imageWidth` and `imageHeight` are set to the rectangle around both panels, scrollbar lane included, whenever the layout changes: the screen opening, a resize, a section opening or closing, never on a scroll. So everything that measures the screen sees both panels: a panel on the menu frame, another mod's buttons by the screen's edges, a recipe viewer keeping its lists clear of the screen (and so of the scrollbar). A click in the gap between the panels is inside the screen, so one with an item held drops nothing. Moving the screen's origin would move everything vanilla placed from it, so vanilla's title is moved back by as much and stays put on screen, and the player's inventory slots and "Inventory" label are moved to go with the inventory panel. The slots are placed every frame from the slots the menu holds then, so one another mod puts in while the screen is open goes with the panel too, and putting the bounds back moves exactly the slots that were moved. A mod reading `leftPos + slot.x` still lands on the slot. Before the screen initializes again (a resize), its bounds go back to vanilla's, so vanilla centers its own image as always.
- **Real slots.** The region changes nothing in the menu. Its sections show the menu's own slots, and a slot library's created slots, through slot elements, so the slots, their indices and the server's sync are vanilla's, and a mod that sorts, restocks or reads a container sees exactly what it would without the region. Only where a slot is drawn changes, written to its `x` and `y` each frame. Hover and clicks go through vanilla's own slot lookup, so a mod asking vanilla which slot is under the mouse gets the right one, and a mod that marks slots through vanilla's `extractSlot` marks them in the list too.
- **Any container, not only the screen's own.** A section is whatever its content shows, so a mod can add one for a container the screen wasn't opened on: an ender chest or a shulker box opened from its item on a chest's screen, say. Give the section a `source` (`Source.of(itemStack)`), so it takes that container's texture, name and art, and content that shows the container's slots, such as a slot library's group on the open menu. A section with no source is the screen's own container.
- **A layout change lays the screen out again.** When the bounds change while the screen is open (a section opening or closing, the list starting or stopping to scroll), the region lays the screen out again exactly as a window resize does, with `Screen.resize` at the screen's own size: Fabric's `BEFORE_INIT` and `AFTER_INIT` run around it, the screen's widgets are cleared, and every mod adds its own again from its init hook at the new bounds, so a button another mod placed by the screen's edges follows the panel it was by. This happens only on such a change, never on a scroll (a scroll never moves the bounds), and at most once a frame however many sections changed since the last one. What a resize keeps is kept: the screen and its menu, the item on the cursor, a drag across slots, the recipe book, the region's scroll, which sections are open (their mods' own state), and what a screen carries over in its own `resize` (the anvil's name, the creative search). What a resize drops is dropped: which widget had focus, and the text of a field another mod creates anew at init without carrying it over.
- **An anchor for each panel.** `ContainerRegion.CONTAINERS` is the container list's rectangle (scrollbar lane included while it scrolls) and `ContainerRegion.INVENTORY` the inventory panel's. Place a panel on either with an `AnchorPanelAdapter` to put a button by the panel it acts on rather than by the whole screen. Both are absent on a screen the region is not on. `ContainerRegion.anchor(sectionId)` is one section's rectangle, across the list from the top of its title to the bottom of its content, moved by the scroll and cut at the list's viewport, for a button that acts on one box. It is absent while that section is hidden or scrolled out of view, so the button hides with it. The section can be another mod's, and need not be declared yet when you ask for its anchor.
- **The wheel, last, from anywhere.** The region scrolls on a turn of the wheel nobody else used: not the screen (vanilla's bundle over a slot), not any other mod's handler, not a panel's element. It listens after every other listener of Fabric's `afterMouseScroll`, whenever they registered, and since its panels claim nothing the turn goes to the screen first wherever the mouse is. A mod that uses the turn keeps it, and the region stays put: Mouse Tweaks, for one, answers "used" over any slot, empty or not, so with it installed the wheel over a slot moves items and the region scrolls only off the slots. Over any other panel the panel's elements get the turn first, as always; one they don't use scrolls the region. Nothing detects any mod.
- **Shift-click lands in view.** A quick move into one of the region's slots that is scrolled out of view scrolls the region until that slot shows whole. A slot the region has drawn before is shown in one move; one in a section never drawn yet is found a page a frame. A quick move out of the region, into the inventory, scrolls nothing. One that lands in a hidden section scrolls nothing either: that section's `onHiddenLanding(...)` runs instead, so its mod can show it (pick its tab, say). MenuKit shows nothing by itself.
- **Hidden sections' slots are off.** While a section's own condition doesn't hold (its `visibleWhen`, its mode scope, its screens), its slots answer `isActive()` false on the client, so nothing draws, hovers or takes a click there, and a slot library's element leaves them out. A slot is a section's once the region has drawn it there. A container's own slot that no section has drawn yet (not the player's, not a slot library's created one) is the screen's own container's: the first section on the screen with no `source`, shown or not, unless turning it off would hide a section that shows (one that presents it itself). The server's slots are never touched.
- **The fitted frame.** `ContainerRegion.fitted(scope, screens)` makes the list and the inventory panel on those screens one frame, as vanilla's image is, as tall as the shown sections need, so it is shorter than the screen's own container part where they are smaller: a 3-row box shown on a double chest's screen shrinks the frame, centered as the list grows. Each shown section's art runs straight on into the inventory part, under a resource pack too, and the grid ends where vanilla's does, 3 pixels above "Inventory". A section's title sits where vanilla's does, tab row or not, so sections as tall as a vanilla container's (a 3-row grid and its title) make that container's own frame, in the same place on screen. Tab rows (Container tabs) stand out from the frame without moving it, as they do on a vanilla screen's own frame, until one would cross the window's margin: switching between a region screen and a vanilla one of the same size moves neither the frame nor the row. A tab row between the two panels splits the frame back into two, still fitted, with the row in the gap. Every other screen keeps the list.
- **Carrying an item to an edge** scrolls it, faster nearer the edge: from 8 pixels inside the viewport's top or bottom edge, full speed at the edge and 12 pixels past it, which below stops short of the inventory's first row.
- **Smooth.** It scrolls by pixels, never whole rows, and a slot across its edge is cut there (Slot rendering).
- **Titles and names.** Title a section that is a vanilla container's with vanilla's translation key (`Component.translatable("container.shulkerBox")`, or the screen's own title). A resource pack whose art covers the title strip blanks those keys, and with one container on the screen the section's title goes blank with vanilla's. With two or more sections shown, a section whose title comes out blank shows a name instead, so the player can tell them apart. The name comes from the section's container, in the player's language and never blanked by packs: its `source`'s custom name, else its block's name ("Lime Shulker Box"), and for a section with no `source`, the screen's own container, the block the screen was opened on. `name(...)`, read every frame, overrides that, for a section with no block behind it. A section with neither is called by vanilla's own English for its title's key ("Shulker Box"). Sections that would show the same name are numbered ("Lime Shulker Box 1", "Lime Shulker Box 2").
- **Resource packs.** Both panels follow the pack's container art, as vanilla's own screen would: the list takes the look of the screen's container texture, the inventory panel the inventory half of it. A section's container texture comes from its `source`'s block: the shulker box's for a shulker box, the chest's for a chest, ender chest or barrel. A section with no source, a source with no block, or a block of another kind takes its `texture(...)`, vanilla's chest by default. Its slot frames take that texture's slots, and its part of the list is a slice of that texture's panel: the list's sides and fill there are that texture's, from just above the section to the next one, so a shulker box in a chest's list looks as it does on its own screen. The list's top is the first section's and its bottom the last's; where two sections meet, the colors simply change. MenuKit adds no color of its own. Text keeps vanilla's colors wherever they read on the pack's fill, and takes one made from the fill where they would not. A section whose fill differs from the first section's is a block of its own, so its content moves down 2 pixels and its title sits inside the block as vanilla's sits inside its art, and the first section's title moves right, clear of the list's top corner, where a pack decorates that corner. [Resource packs](resource-packs.md) has the rest.
- **Per-section art (OptiGUI).** With OptiGUI 2.x installed, a pack's rules can give a container its own art by its block (a lime box), its name ("Ores"), its biome or its height. OptiGUI picks that for a whole screen; the region looks up each section's own. `source(...)`, read every frame, names the container a section shows: `ContainerRegion.Source.of(blockEntity)` for a placed container, `Source.of(itemStack)` for one opened from its item (its block and so its dye, and the name the player gave it; where it is, the player is). An item that isn't a block gives no block, and the rules then match the section by name and place only. The rules replace the section's own texture, the one its block gives. A section with no source is the screen's own container, and takes the art for the block the screen was opened on (the one under the crosshair as it opened, when it holds a container of the screen's size and the screen has its title), else what OptiGUI picked for the screen. A source that gives `null` takes what OptiGUI picked for the screen, and so does the inventory panel. Without OptiGUI, a source still gives the section its texture and its name. [Recipe](recipes.md#a-shulker-box-from-an-item-and-one-placed-in-the-world-each-in-its-own-art).
- **Slot groups.** A section of a slot library's group needs no condition of its own when its content hides itself with the group. SlotKit's `SlotGroupElement.of(groupId)` does: it hides while its group is not on the open menu or not revealed, or while every one of its slots is past its active count ([recipe](recipes.md#stack-containers-in-one-scrolling-column-above-the-inventory)). The screen's own chest grid is a slot group too (`SlotGroupId.category(SlotGroupCategory.CHEST_STORAGE)`), and a single slot is SlotKit's `SlotElement.builder().slot(address).build()`. Slot elements, addresses and slot groups are SlotKit's ([SlotKit's concepts](https://github.com/trevorschoeny/slotkit/blob/main/docs/concepts.md)).
- **Sections for what opens at runtime.** A mod that lets the player open as many boxes as they like can't declare a section for each one ahead of time. `ContainerRegion.sections(kind, scope, keys)` declares a kind of section instead. On a screen it is on, `keys(screen)` is read every frame and gives the keys open there now, of any type with `equals` (a slot library's group instances, say). Each key gets a section, built from the key by `section((key, builder) -> ...)` the frame it first appears, and a tab if the kind has `tab((key, builder) -> ...)`. Both builders are the ones `section(id, scope)` and `ContainerTabs.tab(id, scope)` return, without `declare()` and without targeting, which is the kind's (`on(...)`, `onMatching(...)`). A section stays, the same elements, for as long as its key is there, and goes with its tab when the key does. A new screen starts with none. A kind's sections stack by their order, then by the kind's id, then in the order of the keys, and its tabs do the same in their row, so keys in the order they opened put the newest box last. Everything else is a section's as usual: the title and source, a hidden one's slots off, `onHiddenLanding`, the view staying put when one above it goes.

[Recipe](recipes.md#stack-containers-in-one-scrolling-column-above-the-inventory).

## Container tabs

`ContainerTabs.tab(id, scope)` puts a tab, like the creative inventory's, on an edge of the container region's panels (7.4.0). MenuKit draws the row, hit-tests it, and pages it when it overflows; everything else about a tab is the mod's, read every frame: what a left click does (`onClick`), its icon, an item (`icon(Supplier<ItemStack>)`) or a GUI sprite of the mod's own (`icon(Identifier)`, drawn 16 pixels square where an item goes), its `tooltip`, its `order`, whether it shows (`visibleWhen`, and its mode scope), whether it draws selected (`selectedWhen`) and whether it is grayed and takes no click (`disabledWhen`). MenuKit keeps no selection, so a tab is selected exactly while the mod says so. Like a section, a tab is on every container screen the region is on unless `on(...)` or `onMatching(...)` narrows it, and it is a declaration that freezes with the rest.

- **Four edges, one row each.** `edge(...)` is `CONTAINERS_TOP` (the default, above the container list), `CONTAINERS_BOTTOM` (below it), `INVENTORY_TOP` (above the inventory panel) or `INVENTORY_BOTTOM` (below it). Every mod's tabs on one edge share one row, left to right by `order`, ties by id. A row with no tab showing takes no room.
- **Room made, never over a slot.** A row stands outside its panel, as deep as its tallest tab (25 pixels for a full-size one), and the region counts it: in the block it centers and fits on the screen, and in the screen's bounds, so other mods' buttons and recipe viewers keep clear of it. A row between the two panels stands in the gap between them, widened to hold it.
- **Vanilla's creative tabs.** Top tabs on a top edge, bottom tabs on a bottom edge, so a resource pack that restyles creative's tabs restyles the row. A selected tab runs into its panel's frame, open into it as creative's does; the others stop at the frame. The first tab is flush with the frame's left edge.
- **A click.** A left click on a tab runs its `onClick` with vanilla's click sound, an item on the cursor or not; the click goes no further, so a held item is neither dropped nor placed. A disabled tab takes the click and does nothing. Other buttons are not the row's.
- **Overflow.** Past what fits, vanilla's page arrows at the row's ends move it a tab at a time. A tab that starts drawing selected comes into view. There is no wheel on the row; a mod that wants the wheel to switch tabs listens for it itself.
- **On a screen's own frame too.** Where the region isn't up (the player's inventory, a shulker box, a chest with no section showing, a mod's own container screen), a `CONTAINERS_TOP` row stands on the screen's own frame's top edge and an `INVENTORY_BOTTOM` row on its bottom edge (Fluorite). The two middle edges have no gap to stand in there, so their tabs don't show. The screen keeps vanilla's layout, and screens of one size put the row in one place, so a mod that opens one in place of another shows a steady row. Vanilla's are nearly one size: the inventory is 176 by 166, a shulker box 167 tall and a single chest 168. `ScreenFrames.stretch(screen, seam, by)` makes one exactly the size of another (Fluorite): the frame gains `by` rows at row `seam` of its own layout (or loses them, with `by` negative), the screen's image drawing in two parts with the seam row repeated between them. Vanilla centers it as it does any screen of that size; what is above the seam keeps its place in the frame and everything from the seam down, slots and labels, moves down with the bottom. `stretch(InventoryScreen.class, 81, 1)` gives the inventory a shulker box's frame, with one more blank row above the inventory's rows. No row stands on the creative inventory, which has tabs of its own.
- **Paging carries over.** A screen opened in place of another keeps each row's page; it starts over once the player is back in the world.
- **A tab per key.** For tabs that come and go at runtime (one per box the player has open), `ContainerTabs.keyed(id, scope, keys)` declares a list instead: `keys`, a `Supplier` of a list of any type with `equals`, is read every frame a container screen is open, and `tab((key, tab) -> ...)` sets up each key's tab as `tab(...)` would, the frame the key first appears. The tab is kept while the key is there, so the row's page and a selected tab kept in view follow the key wherever the list moves it. The list's tabs stand together in the keys' order, at the list's `order` and `edge` among the other tabs, on the screens its `on(...)` names (Fluorite). The page stays on its first tab in view as tabs before it come and go.
- **Groups.** A keyed list with a `header(h -> ...)` is a group (Fluorite): the header, set up as a key's tab is and named by the list's id, and the keys' tabs after it as its sub-tabs. The header shows while its own `visibleWhen` holds, keys or none, and the sub-tabs only with it. What a click on the header does is its `onClick`, the mod's: show the header's own page, or pick its first sub-tab. When the sub-tabs are out is `expandedWhen(...)`, read every frame (always, by default): only while the group holds the selected tab, always, or on the mod's own conditions. How they move is MenuKit's and has no options. They slide out from under the header to its right in 200 milliseconds as the group opens, the tabs after it moving over to make room, and back under it as it closes, and a turn mid-way goes back from where they are. On a screen's first frame since the player was in the world, every group stands as it is, so opening the inventory doesn't play a slide. The arrows page through the tabs that are out: a closed group is its header, an open one its header and its sub-tabs. A closed group's sub-tabs take no click. A mod that moves through tabs with the wheel works out the order from its own keys and its own open rule.
- **Sizes.** `size(width, height)` sets a tab's width and how far it stands out from the frame, at least 8 each; the default is 26 by 25. `tabSize(width, height)` on a keyed list sets every key's tab's, before a key's own `size`. A group's sub-tabs are 18 by 17 by default, about two-thirds of a tab. Every tab stands on the frame, so tabs of different heights share their line, and the row is as tall as its tallest tab. The sprite keeps its corners and edges whole and cuts or repeats its plain middle.
- **Icons that play.** A tab's icon is 16 pixels on a full-size tab and smaller in proportion on a smaller one. `icon(item, look)` draws the item as an `ItemAnimation` at the frame `look` gives each frame, the same `ItemAnimation.Frame` a slot look gives, run by the mod's own `Transition`: a box opening on the selected tab, say. The whole draw scales with the icon, so a lid standing past the item's box shrinks with it.

To show one container at a time under the tabs, as the creative inventory shows one page, give each section a `visibleWhen` that reads the mod's own pick and an `onHiddenLanding` that sets it, give each tab an `onClick` that sets it and a `selectedWhen` that reads it, and declare the screen fitted. [Recipe](recipes.md#show-one-container-at-a-time-under-tabs).

## One styling change

MenuKit draws a pressed look on every vanilla button and every YACL controller while it is held down, including buttons MenuKit did not create. It is always on and changes nothing but the drawing. It is the one change MenuKit makes to how vanilla looks. Otherwise the library leaves vanilla's appearance and behavior to the mods that use it.
