6.0.0 (unreleased, in progress): one of everything. Requires MenuKit 6.0.0. Breaking; the migration guide lists every change.

Containers has its own root package, `com.trevlar.menukit.containers`; every import changes. Containers starts on a dedicated server, and a player can join it. On the server a created slot is addressed as a created slot and its group has its category, so operations, vetoes and gates judge it the way singleplayer does. A mod that registers a slot-state channel no longer crashes the server. `MKCMenu`'s screen is set on the client with `menu.screen(MyScreen::new)` from your client initializer; `MKCMenu.Builder.screen(...)` is gone, since naming a screen class in common code crashed every dedicated server.

A created slot's address comes from `Address.createdSlot(MKCSlots.groupId(panelId, groupId), index)`; `CreatedSlotAdapter.addressOf`, `MKCContainerPanel.address` and `MKCScreenHandler.address` are gone. Fixed: a created slot could have one index on the client and another on the server. Parity slots were added to a menu in the order mods initialised, and a client and a server with different mods can initialise in different orders, which desynced the slot. They are now added sorted by panel id, the same on both sides. Storage attachments, slot-state channels, container panels and menus are declared at init; a late one throws.

`SlotGroups.of(slotRef)` names a created slot's own group, so a veto can tell a pocket from the main inventory. Adds API and breaks nothing.

The gate, Curse of Binding and shift-click routing are MenuKit's. `SlotGate`, `GatingContext`, `GATING` and `BINDING` moved to MenuKit; every gate implementation's import changes and `MKCBehaviorKeys` keeps only `MENDING`, whose seam is Containers'. `QUICK_MOVE`, `SlotSpec.quickMove` and `QuickMoveParticipation` are gone, deprecated since 5.1.0: `SlotSpec.shiftClickOut(false)` and `shiftClickIn(false)` declare the two shift-click operations at the group rung. `MKCSlotQuickMove.route`, which nothing called, is deleted; a menu's own `quickMoveStack` still routes between its groups. Containers' four gating mixins are gone with the gate; a created slot no longer gates itself, and resolves through MenuKit's slot-level seam by its created address.

Placement is the panel's (MenuKit's phase 4). `MKCContainerPanel.Builder.at(RegionAnchor, padding)` is `at(PanelPosition, padding)`: `at(PanelPosition.region(OutsideRegion.X).priority(20), 7)`; `at(OutsideRegion, padding)` and the pixel `at(supplier, padding)` stay. A container panel needs a placement a container screen can resolve, checked at `register()` on both sides. `MKCSlots.renderGroup` takes a `PanelPosition` where it took a `RegionAnchor`. `MKCScreenHandler`'s panels default like a standalone screen's: the first unplaced panel is the main frame, later ones stack below it with the old gap, and `PanelBuilder.position(...)` takes any placement. `MKCHandledScreen` places, draws and routes its panels through a standalone host that knows their slot grids: its opaque panels block what they cover while their own slots stay live, and its panels take part in claims and modals with anything injected onto the screen. A panel's own created slots stay live under its claim, and a slot a different panel covers is inert.

Elements are built by builders (MenuKit's phase 5). `MKCScreenHandler.PanelBuilder`'s positional element adders (`button`, `text`, `icon`, `horizontalDivider`, `verticalDivider`, `itemDisplay`, `progressBar`, `toggle`, `checkbox`, `radio`, `infoBox`) and its trailing `tooltip(...)` are gone with the constructors they duplicated; add any element with `.element(X.builder()...build())`. `SlotElement.presentsSlotAt` and `SlotFlowElement.presentsSlotAt` take an `InputContext`.

The server trusts nothing a client sends about slot state, panels or menus. Every slot-state write a client sends is judged: the channel exists, the value parses with its `StreamCodec` and the canonical re-encoding is stored, the write names the player's open menu and an active slot on it, the channel's writer rule allows it, and the player is within a write rate. A `SHARED` channel refuses every client write until it declares who may write, the sixth argument of `MKSlotState.register`: `(player, slot) -> ...`. A refused write changes nothing and the writer gets the server's value back. Writing the default removes the entry, and reading never creates one, so opening a container no longer grows its saved state. Values travel as the channel's `StreamCodec` bytes, not NBT, and a client that cannot decode one skips it instead of crashing. An update reaches only the menu it names; it used to land on any slot with the same index. The slot state a shulker box carries as an item is no longer sent to every client. `MKSlotState.registerPortable` makes another container's state travel with its item. Every packet has a new id, `menukit-containers:v1/...`.

Containers requires itself on both sides. A server with it checks, before the world loads, that a joining client has it, and disconnects one that does not with a message naming MenuKit and MenuKit: Containers and linking their pages. A client with Containers on a server without it builds no created slots and sends nothing Containers-only. Created slots are projected onto every menu the server opens on both sides, so a lectern no longer disconnects a player when parity slots are registered.

Containers has a client source set, and the compiler keeps screens out of common code. A custom menu's handler is its slots and its panels as the server knows them (`MenuPanel`: an id and whether it is shown); `MKCScreenHandler.builder(type)` returns a `SlotLayout` whose panels take groups, `hidden()`, `toggleable()`, `pairsWith` and `rightClick`, and shift-click routing is `QuickMoveRouter`. How each panel looks moves to the client, on MenuKit's `Panel.Builder`: `ClientMenu.of(menu).panel(id, p -> ...)`, with `.screen(MyScreen::new)` and `.requestOpen()`. Visibility is the server's, synced to the client; a player's toggle is honoured only for a `toggleable()` panel. `MKCMenu.Builder.validWhen(predicate)` says who may open a menu and for how long; without it a client cannot open it and it stays open while the player is alive. A container panel's chrome and screen scope move to `ClientContainerPanel.of(id).chrome(...).parity(...)`, and `MKCSlots.renderGroup` to `ClientSlots.renderGroup`. `SlotElement` and `SlotFlowElement` are built by builders: `SlotElement.builder().slot(group, index).at(x, y).build()`. A slider in a custom menu no longer stops a dedicated server.

5.1.0: Created slots follow MenuKit's slot operations. Requires MenuKit 5.1.0. This release adds API and breaks nothing.

Shift-clicking into or out of a created slot now goes through the same shift-click in and shift-click out operations as a vanilla slot. A locking mod's veto covers pockets and other created slots without any extra work from you.

Created slot groups appear in MenuKit's slot group list without a menu open. Groups on a container panel are listed from mod init. Groups added with `MKCSlots.onto` are listed once a menu carries them, or from init if you call `SlotGroups.declare`.

`SlotSpec.quickMove(...)` and `MKCBehaviorKeys.QUICK_MOVE` are deprecated and will be removed in 6.0.0. They still work, and `quickMove` now sets the two shift-click operations for you. New code should call `set(BehaviorKeys.SHIFT_CLICK_OUT, ...)` and `set(BehaviorKeys.SHIFT_CLICK_IN, ...)`.
