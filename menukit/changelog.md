6.0.0 (unreleased, in progress): one of everything. Breaking; the migration guide lists every change.

MenuKit runs on servers. The code that runs on a server and the code that touches a screen are in separate source sets, so a server class that reaches a client class does not compile. MenuKit's common initializer is `com.trevlar.menukit.MenuKit`; `MK` is the HUD facade and no longer an entrypoint. The window's server tier is part of MenuKit and always present, so a MenuKit-only mod's server declarations take effect. Container identity is MenuKit's too: a vanilla slot's address is the same with or without Containers, and a registered block-entity resolver is now consulted. Its manifest is universal, so Containers, which depends on it, starts on a dedicated server; neither had ever started on one. Vanilla menus' slot groups are resolved on both sides, so a server knows a hotbar slot's category and the operations cascade, `AppliesTo` and `SlotGroups.of` answer there as they do in singleplayer.

One engine answers every key: both tiers are one store walked one way, and clearing a declaration removes it, so nothing piles up per player or block. An `Address` saves as text: `asString()`, `parse` and `CODEC`, with one public minter per kind, `Address.createdSlot(group, index)`, `Address.panel(id)` and `Address.panelElement(id, declId)`. A slot group and its cascade group are one identity through `GroupKey.of(SlotGroupId)`, and a vanilla slot gets a group rung as well as its category's. `SlotGroupId.Vanilla` is `SlotGroupId.Category`, with `isVanilla()`.

Declarations freeze once every mod has initialised, before any menu can open: a late `define`, `veto`, `declare`, `register` or `addTo` throws, naming the call. Changing a slot at runtime is still fine. Nothing depends on which mod loaded first: two mods declaring the same thing is an error at the second, and where several coexist their order is sorted. `SlotGroups.entryKey` is gone; save a group by `SlotGroupId.asString()`.

Tabs. `Tabs` is a tab strip with the selected tab's body below it, for tabbed settings menus. It wraps into rows, scrolls sideways, or runs down the left as a sidebar, with vanilla's thin list scrollbar when its tabs overflow and room for a Back button over them. It aligns tabs left, centred, right or to fill each row, hides tabs live, and keeps each tab's scroll position. Selection is your own field, so opening a menu on a given tab is setting it first. `MKScreen.hideTitle()` drops the title band across the top of a screen, so its main panel can start at the top; the title still names the screen for narration. Elements can now take their height from their panel (`fillsHeight()`), which is how a `Tabs` fills a full screen. Other mods add tabs to a named menu with `Tabs.addTo`: an owner's `standIn()` tab holds the place of a tab another mod may add and shows dimmed until one does, other added tabs go `after` or `before` a tab, and the order never depends on which mod loaded first. `Row.width(px)` and `.addSpacer()` pin elements to opposite edges of a row, one thing left and one right with a flexible gap between, for a header with Back at one corner and Reset at the other. `SlotGroups.of(slotRef)` names the slot group a slot is in, so a veto can tell a hotbar slot from a pocket. An operation says which slot groups it can act on with `SlotOperations.define(op, role, AppliesTo...)`: it names vanilla's groups, and every group a mod adds applies unless the operation opts out. `SlotOperations.appliesTo(op, group)` and `groups(op)` read it back, and vanilla's eleven operations declare where vanilla lets them act. A veto that decides by slot group registers as a `SlotOperations.GroupVeto` and is handed the slot's group, worked out once per question instead of once per veto. Save a player's choice about a group under `SlotGroupId.asString()`. A group's id never changes, and the set it is listed in is only for the listing. A group joins a set only from its own namespace and only before its row has been read, so no mod can move another mod's group between rows. `AppliesTo` judges a mod's group that declared a vanilla category by that category first, so a pocket declared as inventory goes where the inventory goes. `SlotGroups.listing()` and `SlotOperations.groups(op)` are cached and rebuilt after a declaration, and slot groups on a menu come in slot order on every run. Operation checks are cheaper: a slot's address is worked out once per menu, and server-side keys skip a lookup that could never answer. Fixed: a `Button` built with width 0 drew no box outside a filling column; a `Dropdown` inside a tab body or a `ScrollContainer` never closed on a click outside it; `ItemDisplay` could not show the count without the durability bar or the other way round; `TextField` reported its starting text as a change; a notification sent from a server thread could break the HUD's drawing of notifications; a YACL release that renamed a method could stop the game at load; a click inside another click lost the acting player when the inner one ended. Adds API and breaks nothing.

One seam per vanilla method, and the gate is MenuKit's. `SlotGate`, `GatingContext`, `BehaviorKeys.GATING` and `BehaviorKeys.BINDING` are MenuKit types now, so a MenuKit-only mod gates a vanilla slot the same way Containers gates a created one, with `Window.slot(address).gate(...)` and `.binding(true)`. MenuKit enforces them at the slot's own `mayPlace`, `mayPickup` and `getMaxStackSize`, at the merge pass of a shift-click, and at hoppers and dispensers, and asks the gate once per vanilla method: the empty pass of a shift-click used to ask a vanilla slot's gate twice and a created slot gated itself a third time. A click is judged once on the client, at its send boundary, and once on the server. The one Containers-only fact a gate reads, whether a player's client can see slot state, is behind `GatingContext.installCapability`. A lock is a veto, in one sentence everywhere: a gate is what a slot is for, a veto is somebody else's no. `WORLD_PICKUP` is `INVENTORY_INSERT`, named for what it gates: every item given to the inventory, from the ground, `/give`, pick block or a crafting grid's returns, through the same two vanilla methods. Its id stays `menukit:world_pickup`. A `SlotRef` carries the slot's `Address`, so a veto that keys on it never derives it. `ClickTags` and `PlayerActions` are internal; the validator checks them through `OperationProbe`.

One host per context, one placement, one claim. Where a panel sits is declared once, on the panel: `.position(PanelPosition.region(...))`, `screenAnchor(...)`, `center()`, `pixel(...)` or `main()`, with `.priority(n)` for stacking and z-order and `.offset(dx, dy)` to nudge one panel. The adapters take only `(panel)` or `(panel, padding)`; `RegionAnchor`, `OutsideRegion.priority` and `InsideRegion.priority` are gone. `PanelPosition.BODY` is gone: a panel with no placement is rejected by adapters and the HUD, and `MKScreen` makes the first one its main panel and stacks the rest below it. A HUD panel is an ordinary `Panel`: `MKHudPanel.builder(...).region(InsideRegion.X).offset(dx, dy).priority(n)`, and `build()` returns it. `MKHudAnchor`, `MKHudPanelDef`, `anchor(...)`, `hideInScreen()`, `showInScreen()` and the HUD `onRender` callback are gone; hiding while a screen is open is part of `showWhen`, and `.custom(...)` draws freely inside the panel. Notifications take `.region(...)` and `.offset(...)` the same way. Each context (container screen, other vanilla screen, slot group, HUD, standalone screen) is one host that sorts, places, draws and routes its panels, and every host draws FLOW panels, then the dim, then overlays, so a vanilla screen gets dialogs and dimming too. Panel declarations freeze with the rest at client start, and ordering is sorted, never registration order; a panel that comes and goes gates itself with `showWhen`. The claim rule is one rule everywhere: an opaque panel takes its whole rectangle, with no holes, and a see-through panel takes only its buttons and other controls. Fixed: a panel anchored to a slot group, and a standalone screen's own panels, did not block what was under them; a slot under one could still be hovered, clicked and tooltipped. An element marked non-opaque inside an opaque panel no longer lets clicks through to what is behind the panel. A panel under a claim, or under a modal it does not belong to, shows no hover; its own tooltips show over its own claim. `InsideRegion.LEFT_CENTER` and `RIGHT_CENTER` now centre the panel vertically on the HUD and on vanilla screens, as they already did for screen chrome. `ScreenPanelAdapter.getOrigin(screen)` takes only the screen.

Elements are lenses, built once, with one vocabulary. Every element has a builder and does not change after `build()`: `Button.builder().label(text).size(60, 16).onClick(run).build()`. The same idea has the same name on every builder: `at`, `size`, `visibleWhen`, `disabledWhen`, `tooltip`, `state(get, set)`, `onClick`, `style`, `opaque`, `declId`. The positional constructors, the `spec(...)` factories and every setter on a built element are gone (an element's `showWhen` is `visibleWhen`, `setElementOpaque` is `opaque`); `Row` and `Column` take built elements. A control that shows a value is a lens and only a lens: `Toggle`, `Checkbox`, `Slider`, `TextField`, `Dropdown` and `DropdownMulti` take a required `state(get, set)`, read it every frame and store nothing, and `RadioGroup.state(get, set)` replaces the group that held its selection. `Toggle.linked`, `Checkbox.linked` and the stateful constructors are gone. `TextField` drops `filter` (vanilla removed it) and consumes Enter only when it has an `onSubmit`; `DropdownMulti` hands its setter the whole new set. Whether a `Section` is open, and a `ScrollContainer`'s scroll, are the element's view state unless you pass a `state`, in pixels for the scroll. Input receives its context: an element's `mouseClicked`, `mouseScrolled`, `mouseReleased`, `keyPressed`, `hitTest` and popover calls take an `InputContext` with the origin and the mouse, so no element keeps a position or a hover state from the last frame, and one `ChildDispatch` routes input the same way in a panel, a `ScrollContainer`, a `Flow`, a `Section` and a `Tabs`. `Button`, `Toggle`, `Checkbox` and `Radio` play vanilla's click sound, take keyboard focus with Tab and a press with Enter or Space, and read to the narrator; `Slider` and `TextField` are vanilla's own widgets, exposed through `widget()`. For settings screens: `Flow.spacer()` pins a control to the right edge of a row at whatever width the panel has, so a label at the left and its control at the right, or a switch and Reset on one header row, need no width handed to a tab's body; `Panel.disabledWhen` greys a whole panel and a container's `disabledWhen` everything in it, labels and section headers included; a horizontal `Divider` with no size fills its panel's width; and `Slider.ofInts`, `Slider.ofEnum`, `Dropdown.ofInts` and `Dropdown.ofEnum` take a whole number or an enum as their state. `SlotRendering.drawItemOutline`, and `ItemDisplay`'s `outline`, draw an item with a line of any colour around its own shape. `Dropdown` and `DropdownMulti` share their popover, and a multi-select's summary now wraps like a single-select's. Fixed: a `Checkbox` or `Radio` whose label wrapped still reported its one-line width, so it could hang past its panel.

5.1.0: An inventory mod can now list every slot operation in the game, show each one to the player by name, and block the ones they pick on the slots they pick. This release adds API and breaks nothing.

Vanilla's slot actions are split into one operation per gesture: click to take, click to place, shift-click out, shift-click in, double-click collect, drag fill, hotbar swap, offhand swap, drop one, drop stack, and item pickup. All of them are on by default. MenuKit enforces them itself, so a mod that depends on MenuKit alone gets them without Containers. Q, Ctrl-Q and F count as the same operations when no screen is open.

Every operation has a display name and a one-line description, read from lang keys (`slot_operation.<namespace>.<path>`), so a settings screen can list them. `SlotOperations.all()` returns vanilla's operations and every operation other mods have defined.

A lock is a veto. `SlotOperations.veto(rule)` refuses an operation on a slot and never overrides what the slot's own mod declared. `SlotOperations.allows(...)` is the single check that vanilla's seams use and that your own operations should use too. A veto knows which player is acting, so a per-player lock can tell a LAN guest's click from the host's.

Clicks your mod sends count as your operation when you wrap them in `SlotOperations.as(...)`. A lock that blocks shift-click then leaves alone the restock that happens to use one. A click sent without the wrapper counts as the gesture it looks like.

When a slot refuses a click, the client does not send it, so the refusal also holds on a server that does not run MenuKit.

Rules set for a slot category now reach vanilla slots. `SlotOperations.inherent(PLAYER_HOTBAR, SHIFT_CLICK_IN, FALSE)` keeps shift-clicked items out of the hotbar and still lets them into the main inventory.

Slot groups can be listed from the title screen with `SlotGroups.all()`. Each group has a player-facing name and a stable id you can save. `SlotGroupSet` shows several groups as one row, which suits a mod that adds many small groups of the same kind.
